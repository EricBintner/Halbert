# TERMINAL

## SUMMARY
The TerminalAccordionDock is NOT orphaned: after the 2026-08-26 deletions it is mounted in the right column of the engaged surface via ContextStage.tsx:63 (HostShell.tsx:45 -> ContextStage -> TerminalAccordionDock), and InlineTerminals is mounted inside AgentChat.tsx:697. The backend->frontend pipe is real and verified by code: executor._run_command publishes spawn/output/complete payloads through terminal_bridge, state_machine._run_tool_streaming drains them into terminal_spawn/terminal_output/terminal_complete SSE events, useAgentStream.applyTerminalEvent writes them into the singleton terminalSessionStore, and AgentChat renders InlineTerminals -> TerminalTile (xterm.js). Tests reproduce the docs' claims: vitest 18/18 passed, pytest 23/23 passed (with the repo .venv; the miniconda `python` on PATH fails 19 tests only because pytest-asyncio is missing), tsc --noEmit exit 0 with zero errors. However, the founder's requirement is only partially met. Inline tiles exist only for the CURRENT turn: every sendMessage mints a fresh session id and resets terminalSessions to [], and AgentChat renders the assistant block only for the last user message, so terminals from earlier turns vanish from the conversation (no tile, no chip) while remaining in the dock, and the dock's jump-to-origin becomes a silent no-op for them. Tiles are rendered as one block after all ToolExecutionCards rather than at each tool's position, and the ToolExecutionCard also prints the same output as a <pre> transcript. Agent-run commands are asyncio subprocess pipes mirrored read-only over SSE (attach:'sse'), not PTYs; only '+ New Terminal' spawns a real os.openpty/os.fork PTY with a working bidirectional WebSocket and resize. A confirmed code bug makes TerminalTile render blank when it mounts onto a session that already has output (short commands, re-expanding a docked/finished session), because the xterm is created asynchronously after the output-write effect ran and nothing replays the buffer. The docking mechanism is an IntersectionObserver at 25% visibility, one-way, with a TetherChip left in place; it has no rootMargin/hysteresis and can fire on mount during the smooth auto-scroll (plausible auto-dock race, not verified live).

## RECOMMENDATIONS
- Persist terminals across turns: keep a conversation-scoped list of assistant blocks (or at least a list of terminal session ids per user message) so InlineTerminals renders for every past turn, and key the store's origin by conversation id rather than per-message session id; clear the store on conversation switch (loadConversation/startNewConversation) by that key. Verify the dock's ⤴ button by asserting the origin element exists and falling back to expanding the row when it does not.
- Fix the blank-mount bug in TerminalTile: after `mount()` creates the xterm, write `session.output` immediately (and set writtenRef to droppedChars+output.length), or hold the latest session in a ref and replay it inside the font-ready callback. # ORCHESTRATION

## SUMMARY
Halbert has no meta-level orchestrator today. What exists is a single-turn agent state machine (`AgentStateMachine.process()`) that is instantiated once per process, given a fresh `session_id` per user message by the frontend, and never receives conversation history, a conversation_id, or any reference to other conversations. The "subagent" layer (`SubagentManager`, `StorageAuditorAgent`, `spawn_subagent`/`await_subagent_completion`) is committed but inert: no production code constructs a `SubagentManager`, `get_agent()` never passes `subagent_manager=`, no `delegate`/`spawn_subagent` tool is in the tool schemas the LLM sees, and the only "subagent" is a deterministic regex-parsing shell probe with no LLM. Conversations exist in three disconnected stores (legacy `/api/conversations` JSON under `~/.config/halbert/conversations`, the agents `ConversationStore` JSON under `~/.halbert/conversations`, and an unused `SqliteConversationStore` with FTS5), none of which the agent path writes to, and none with parent/child links, embeddings, or LLM summaries. Cross-conversation retrieval (`SessionAffinityRouter`) is test-only; `context_handoff.py` is a model-swap context compressor, not a conversation handoff. "Memory" on the live path reduces to `HybridMemorySystem` whose vector store/search calls are guarded by `hasattr` checks that fail against the real `Index` class, leaving an in-process 100-item cache plus self-knowledge search; the LLM has no memory tool and no prompt text mentions memory, prior conversations, or delegation. `runtime/` is a Phase-1 placeholder graph reachable only via a CLI `runtime-tick` command. The relevant backend tests pass (122 passed) when run with the repo `.venv`; with the default miniconda Python 3.9 they fail on environment (no pytest-asyncio, `str | None` syntax). Verdict: stubs — the primitives for a conversation-aware orchestrator are almost entirely absent.

# DESIGN

## SUMMARY
The planning corpus contains two distinct generations of design intent. The 2026-08-21..23 layer (philosophy.md, the-being.md, explorations.md, ROADMAP, FINAL-PLAN) defines the original concept: an LLM that IS the computer, one continuous first-person conversation as the home surface, dashboard pages demoted to summonable modules in a context region, one mind (Haloysius tick + continuity + memory_v2) with background workers as subsystems "not separate personalities", and an explicit rule that the terminal is agent-facing only. The 2026-08-24..25 "Sovereign Host" layer (documentation/sovereign-host-vision/*, OPUS/FABLE handoffs) added Feature A (flowing in-chat PTY tiles that auto-dock into a right-column accordion at <25% visibility with a tether chip and jump-to-origin) and Feature B (a "Continuous Orchestrator Mind": zero-manual-session timeline, a deterministic FTS5 session-affinity router, subagents forked into isolated PTYs that report back as Somatic Blocks, a 03:00 Dream Cycle consolidating threads into SourcePrep concepts). The results docs and the code agree that Feature A is built and reachable (HostShell → ContextStage → TerminalAccordionDock; InlineTerminals + TetherChip + useIntersectionDock; SSE 'sse' mirror transport for agent commands, 'ws' PTY for user shells) but with deliberate deviations: docking is one-way, agent commands are streamed subprocesses not PTYs, jump-to-origin scrolls to the chip rather than restoring the tile, and the dock now lives under HostVitals in the right column while ContextBar moved into the left column (SidePanel, the file the dock was specified against, was deleted on 2026-08-26). Feature B is committed but inert: SubagentManager/StorageAuditor/spawn_subagent/await_subagent_completion, SomaticLifecycle, SQLite+FTS5 conversation store, session_affinity router and context watermark all exist as modules with zero production callers; routes/agent.py constructs AgentStateMachine without subagent_manager or somatic_lifecycle, the storage auditor never emits a SomaticBlock, the conversation store is still per-file JSON, and AgentChat still presents a session-picker dropdown with a "New Conversation" button that the continuous-timeline design explicitly forbids. The docs themselves resolved the key Feature B tension in favour of a deterministic router ("never run an LLM classifier on every keystroke"; subagents spawn only on an explicit tool call or button), which is narrower than the founder's current phrasing of "a meta-level orchestrator agent that is aware of conversations". Founder constraints that any new design must honour are enumerated with sources below: commands staged not executed, never "Sovereign" and label with the onboarding ai_name, never name AI models, canonical tokens only, exactly one conversation surface reached via hostConversation.ts, one personality, Haloysius seam ownership undecided, Dream Cycle opt-in only, and never touch the running embed build.

## SUMMARY
The open-claude-code repo (/Volumes/Thunderbolt/AI/OSS/open-claude-code, v2/src, ~9.8k lines of .mjs) is a thin clean-room sketch, not a faithful Claude Code: its ADRs claim "100% feature parity" (docs/adr/ADR-001-v2-architecture.md:3,268) but the code has no background-task readback, no task notifications, no jsonl transcripts, no session list/resume command, no memory system, and its sub-agent/teams/messaging primitives are declared-but-dead (schema fields ignored, module-level Maps nobody reads, `receive()` never called). # WARP

## SUMMARY
Warp (Rust, ~5.3k files) answers both of Halbert's questions with one load-bearing decision: there is exactly ONE ordered transcript per terminal surface — `BlockList` (app/src/terminal/model/blocks.rs:268) holds `Vec<Block>` plus a `SumTree<BlockHeightItem>` whose items are terminal `Block`s, `Gap`s, banners, and `RichContent` (AI exchange blocks); the viewport (`ViewportIter::next`, block_list_viewport.rs:1950) walks that tree from scroll-top and filters by `TranscriptScope::{Unfiltered,Terminal,Conversation(id)}` (block.rs:86), so 'conversation view' vs 'terminal view' is a filter over the same list, not a split pane. A `Block` (block.rs:297) is a model over three grids (header/rprompt/output) with `BlockState`, exit code, creation/start/completed timestamps, an `InteractionMode` (block/interaction_mode.rs) and per-conversation `AgentViewVisibility`; it holds no PTY handle — the PTY lives in `PtyController` (writeable_pty/pty_controller.rs:85) and block boundaries come from shell precmd/preexec hooks (`BlockId` = `{session}-{n}`, crates/warp_terminal/src/model/block_id.rs). There is no 'parked' block state; the closest primitives are the sticky 'snackbar' command header (block_list_element.rs:289-448), per-conversation hide flags (`should_hide_block`, block.rs:1389), hidden-by-default agent-requested command blocks that auto-expand when long-running (view.rs:19055-19075, 20609-20615), and bookmark floating previews (view/bookmarks.rs:12). The 'attach to a running agent command' feature is a state machine on the block: `InteractionMode::{User{did_user_tag_in_agent},Agent{requested_command_action_id,subagent_task_id,long_running_control_state}}` with `LongRunningCommandControlState::{Agent{is_blocked,should_hide_responses},User{reason: Manual|Stop{should_auto_resume}|TransferFromAgent{reason}}}` (cli_controller.rs:31-155), plus an agent-facing output snapshot (`formatted_terminal_contents_for_input`, interaction_mode.rs:574, 1000-row window around a `<|cursor|>` marker) polled by `ShellCommandExecutor::action_result_future` (shell_command.rs:563) with 2s default wait, 120s cap and a user 'Check now' force-refresh. Multi-agent is a global registry singleton `BlocklistAIHistoryModel` (history_model.rs:251: live conversations per terminal surface, `children_by_parent`, `agent_id_to_conversation_id`), a 7-state `ConversationStatus` including `WaitingForEvents` (conversation.rs:4721), a `run_agents`→`StartAgentExecutor` fan-out (run_agents.rs, start_agent.rs:34), a parent inbox `OrchestrationEventService` that drains child messages/lifecycle events into the parent's next LLM request (orchestration_events.rs:73,260), a single ancestor-filtered SSE stream with persisted sequence cursor and kill tombstones (`OrchestrationEventStreamer`, orchestration_event_streamer.rs:280,348), an idempotent `OrchestrationChildTracker::observe_child(ChildSignal)` (orchestration_child_tracker.rs:52-135), and a `wait_for_events` tool with watchdog (wait_for_events.rs:22-45). Notifications are a separate `AgentNotificationsModel` that fires only on Success/Blocked/Error, dedupes by origin, marks read-at-creation if the surface is visible, suppresses completion when a queued prompt will auto-fire, caps toasts at 2, and hands off to native OS notifications with a routable context payload (agent_management_model.rs:352-500, toast_stack.rs:104-160, workspace/view.rs:16051-16070). Recall/navigation is a normalized `AgentConversationEntry` (entry.rs:74) resolved at accept-time plus a pill bar/breadcrumb model with pinned+status ordering, subtree rollups and a drill-down anchor rule (orchestration_topology.rs, specs/QUALITY-567, specs/code-1946). Halbert already has InlineTerminals/TerminalAccordionDock/useIntersectionDock (one-way dock, MAX_VISIBLE=3) and a `SubagentManager`, so feature A is partial and feature B is at the 'spawn/complete' stage; the lift is the interaction-mode state machine, the agent-readable snapshot, the conversation registry+status+inbox trio, and the notification/recall policies — not the Rust UI machinery.

## OPEN QUESTIONS
- Where should Halbert's agent-readable terminal snapshot come from: a Python screen emulator (pyte) fed from the PTY master, or a request to the frontend for xterm.js's buffer? Warp does it server-side in the same process as the PTY (shell_command.rs:563 → interaction_mode.rs:574); the Python route keeps the agent independent of an open browser but duplicates parsing.
- Does Halbert want block boundaries for interactive shells (user-typed commands in an attached PTY) or only for agent-issued one-shot commands? Warp's whole block model depends on shell precmd/preexec hooks minting block ids (block_id.rs); Halbert would need a bootstrap script or OSC 133 integration per shell to get exit codes and timings for user-typed commands.
- Halbert's `useTerminalSessions` caps visible xterms at 3 and the backend `TerminalSessionManager` defaults to `max_sessions=2` (session_manager.py:42); with orchestrated subagents each owning a PTY surface (Warp's hidden-pane model), what is the intended session budget and what happens to a subagent that needs a shell when the cap is hit?
- Should the orchestrator be an ordinary conversation with extra tools (Warp's choice — no special orchestrator process; run_agents.rs, wait_for_events.rs) or a distinct backend service in Halbert? The Warp design keeps recall/notifications uniform because the orchestrator is just another `AIConversation` with `children_by_parent`.
- Which of Warp's status states does Halbert need in its subagent lifecycle: `waiting_for_events` and `blocked{action}` are load-bearing for both the aggregated orchestrator status and the notification policy (QUALITY-780; agent_management_model.rs:528); Halbert's `SubagentHandle.status` currently has only queued|running|completed|failed|cancelled (subagent.py:43).
- Warp persists conversations to SQLite and restores the orchestration tree + event cursor on restart (children_by_parent rebuilt from DB; last_event_sequence). Is cross-restart recall of subagent trees in scope for Halbert's first iteration, or is in-memory sufficient?
