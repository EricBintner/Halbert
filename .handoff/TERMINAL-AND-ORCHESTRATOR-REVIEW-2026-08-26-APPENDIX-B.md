## SUMMARY
Claude Code's "continuity" on this machine is not one mechanism but five stacked ones, and the real artifacts show it is far more mechanical than the OSS docs suggest. (1) The per-session JSONL under ~/.claude/projects/-Volumes-4TB-BAD-Halbert/ (23 files, 56 MB, ~24k rows) is an append-only, parent-linked (parentUuid) event log: on --resume the whole tree is replayed as-is — a resume adds only an isMeta "Continue from where you left off." row, a SessionStart:resume hook attachment, and fresh delta attachments (skill_listing, agent_listing_delta, mcp_instructions_delta, task_reminder); nothing is summarised. (2) Compaction is separate and event-driven: a system row subtype=compact_boundary with compactMetadata {trigger auto|manual, preTokens, postTokens, preservedMessages.uuids} followed by a user row isCompactSummary=true holding a model-authored 9-section summary plus a pointer to the full JSONL path; auto triggers at ~166k–178k tokens and lands at 8k–40k; the raw rows before the boundary stay on disk untouched (the JSONL IS the hidden session, the summary IS the working context). No Halbert session has ever been compacted — the 62 compactions on this machine are all in other projects. (3) Memory is two-tier and NOT relevance-scored: the whole MEMORY.md index (17 one-line entries, ~3.5 KB) is seeded into the first user message as a system-reminder "claudeMd" block ("Contents of .../memory/MEMORY.md (user's auto-memory...)"), which is never persisted to the JSONL; individual notes are pulled on demand by the model's own Read tool, and are written by the model's own Write/Edit (toolUseResult type "create"/edit; file-history-delta rows track the memory dir), with a staleness system-reminder ("This memory is 3 days old...") added on read. (4) Skills are progressive disclosure: only name+description lines are in context (skill_listing attachment), the body arrives only when the model calls Skill and the tool_result is just "Launching skill: <name>" while the body is injected out-of-band; a SessionStart hook (matcher startup|clear|compact) re-injects the one bootstrap skill in full after every compaction. (5) Background work continues via a queue: a subagent gets only its prompt (agent-*.jsonl row 0 has parentUuid null, no parent history), and when it finishes a queue-operation enqueue writes a <\task-notification> row that becomes a user row with origin.kind "task-notification", promptSource "system", carrying <output-file> and the full <result>. Halbert already has the substrate for each tier: agents/conversation_sqlite.py (FTS5 over messages, unused) is the hidden-session log; conversation/summarization.py (5-tier cascade, imported only inside context/assembler.py:365) is the compact summary; memory/writer.py + a curated index file is MEMORY.md; config/prompts/v2/tools/*.xml via prompts/loader.py is already SKILL.md-shaped and only needs description-only listing plus on-demand loading; the per-turn tick in integrations/cognition_wiring.py:157 is the natural place to emit the topic-boundary and memory-promotion events, and the state machine already has the StreamEvent channel to carry a task-notification-style system turn.

## SUMMARY
Claude Code implements continuity via nine orthogonal layers: (1) **Auto-memory** persists Claude's session-specific learnings in an index + topic docs, loaded partly at startup and on-demand later. (2) **CLAUDE.md hierarchy** (managed/user/project/local scope + path-scoped rules) provides persistent instructions with lazy loading. (3) **Skills** bundle reusable workflows with frontmatter metadata, loading only on invocation. (4) **Sessions** preserve full conversation history, model, permission mode, and /goal state across resume boundaries. (8) **Checkpointing** automatically captures file state before each prompt, enabling rewind to any prior point. (9) **Goals** implement open-ended loops toward user-specified conditions, with Haiku as an evaluator that judges each turn. For a sysadmin agent product, map these to: database-backed memory with topic isolation, config-driven rules with glob matching and lazy loading, skill registry with frontmatter parsing, session DB with JSONL transcripts, summarization engine, subagent orchestrator with tool allowlists, hook dispatcher with event emitter, checkpoint snapshots with GC, and goal evaluator with background check-in logic. ### 1. Auto-memory (MEMORY.md + per-topic files)
EVIDENCE: https://code.claude.com/docs/en/memory.md — 'Auto memory section', 'Storage location', 'How it works'
DETAIL: **Location and Structure:** Auto-memory lives at `~/.claude/projects/<project>/memory/` (where `<project>` is derived from the git repository path). The directory contains `MEMORY.md` (an index) plus one topic file per memory. **Loading:** The first 200 lines or 25KB of `MEMORY.md` (whichever comes first) are loaded into every session. Topic files (e.g., `user_role.md`, `feedback_testing.md`) are NOT loaded at startup—Claude reads them on demand using file tools when needed. **What Claude writes:** Four types: `user` (role/expertise/preferences), `feedback` (corrections and confirmations), `project` (ongoing decisions/work), `reference` (where info lives outside the repo). Claude skips facts it can derive from code and anything already in CLAUDE.md. **Size limits & index rules:** If `MEMORY.md` exceeds its limits, Claude Code returns an error telling Claude to rewrite it (keep one line per entry, move detail to topic files, merge/drop stale entries). Topic files have no size limit. Machine-local only; shared via git across worktrees within the same repo. # WARP

## SUMMARY
Warp never decides "continue vs new" by content on the client. A prompt always goes to the conversation currently selected on the terminal surface (`context_model.selected_conversation_id` -> `agent_view_state.active_conversation_id`); "new" is a user gesture (keybinding with an armed confirmation, /new, prompt-suggestion flag) or a SERVER-issued tool call. Topic splitting is that server tool: the agent emits `SuggestNewConversation { message_id }`, the block renders "It seems like the topic changed. Would you like to make a new conversation?" with Start/Continue buttons, and on Accept the server replies with a `StartNewConversation { start_from_message_id }` client action; the client then MOVES (not copies) every exchange from that message onward into a freshly created conversation, marks the old one completed, and switches the surface's selection. Nothing is summarised across the split; the carry-over is the literal tail of exchanges, and the old conversation keeps its earlier context. Context bleed is handled separately by server-driven compaction (`/compact`, `MoveMessagesToNewTask` replacing a message range with a summary subtask) and by the per-model `context_window_limit` sent with each request. Terminal context is attached by tagging blocks with conversation ids (`AgentViewVisibility` pending/attached sets, persisted in `blocks.agent_view_visibility`), but the LLM payload is a copied, secret-redacted, 50-line-capped `BlockContext` embedded in the UserQuery, and the full `task_context.tasks` transcript is re-sent every request with the server token. Recall across conversations is an agent tool, not a UI: `FetchConversation` materialises a past conversation's tasks into a temp directory of per-message YAML files, and a server-side `ConversationSearch` subagent then globs/greps/reads those files (phase UI: Listing -> Grepping -> Reading). Local persistence is `agent_conversations` (json `conversation_data` + write-time `summary` column) and `agent_tasks` (protobuf blobs); on startup only the newest 200 summaries are indexed and full transcripts hydrate lazily; titles are server `UpdateTaskDescription` on the root task, falling back to initial query. Persistent knowledge is WARP.md/AGENTS.md project rules (sent as `ProjectRules` context), cloud-synced `AIFact::Memory` rules the server injects when `rules_enabled`, agent-suggested rules/workflows in every response, and a server-side agent memory store; there is no client-side cross-conversation memory. NL-vs-shell detection is a layered pipeline (allowlists, `["yes","continue","do it","approve"]` follow-up list gated on the last block being an AI block, fuzzy history match at 0.9 ratio, then a bert-tiny ONNX classifier with a word-list heuristic fallback). Halbert already has the seed of the missing piece Warp lacks (content-based `SessionAffinityRouter`, FTS5 messages index, tiered `ConversationMemory`), but today the dashboard mints a random session id per message and `routes/agent.py` never passes `conversation_history`, so there is no continuity at all to modularise yet.
