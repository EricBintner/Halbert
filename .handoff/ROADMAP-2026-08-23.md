## 0. The Problem in One Paragraph

Halbert has two RAG systems doing the same job. ChromaDB (`rag/embeddings.py`, `rag/retriever.py`, `index/chroma_index.py`) is a basic hybrid retriever with no structural awareness. SourcePrep (`integrations/sourceprep_client.py`, `integrations/sourceprep_retrieval_backend.py`) is a sophisticated retrieval system with intent-aware search, knowledge routing, scope filtering, LOD compression, trace graph expansion, concepts (rationale store), and observations (ops memory). The Phases A-E integration bolted SourcePrep on alongside ChromaDB instead of replacing it. Meanwhile, 63,932 docs are sitting in `data/` as JSONL files waiting to be indexed, the intake pipeline design is ready but assumes ChromaDB as its backend, and chat.py is scheduled for retirement. This roadmap consolidates all three tracks into one sequenced plan.

**What this roadmap covers vs. what it doesn't:** Phases 0–4 are the *infrastructure spine* — retrieval, intake, conversation consolidation. They are prerequisites for the two proof slices in `the-being.md` §7, but they are not the slices themselves. The slices (proactive config worry + reactive "how are you") require additional capability layers — the config physiology brain, the proactive channel, the why data model, the ambient surface — tracked in Phases 5–8 below. The infrastructure spine must land first; the slices land on top of it.

## 1. Decisions Already Made

| Decision | Rationale |
|----------|-----------|
| Docs go into SourcePrep, not ChromaDB | SourcePrep's RAG is 2-3 generations ahead. ChromaDB embeddings (all-MiniLM-L6-v2) can't be reused in SourcePrep (nomic-embed-text-v1.5). Building ChromaDB ingestion now is throwaway work. |
| Intake pipeline wires into agent.py only | chat.py is being deprecated (A1). Wiring intake into chat.py as a transition step is wasted work. |
| JSONL docs are grouped per-source, not one file per doc | 30K+ individual files is excessive filesystem I/O for SourcePrep's build. Grouping by source (one markdown file per JSONL, each doc as an H2 section) reduces to ~60 files and lets chunk_markdown() split on headings. |
| Three stores, clear ownership | SourcePrep (system knowledge + docs + rationale + ops memory), memory_v2 (episodic conversation history), SQLite (findings + proposals + approvals). |

## 2. The Corpus

From `data/manifest.json` (updated 2026-08-23):

| Platform | Sources | Docs | Format |
|----------|---------|------|--------|
| Linux | 25+ JSONL files | ~22,800 | JSONL (text + metadata, or content + title + url) |
| macOS | 5 JSONL files | ~16,470 | JSONL (same formats) |
| BSD | 2 JSONL files | ~226 | JSONL (same formats) |
| **Total** | **~32 JSONL files** | **~63,932** | All JSONL |

JSONL record schemas vary by source:
- **Man pages:** `{"text": "...", "metadata": {"source_type": "man", "man_page": "al(1)", "os": "linux"}}`
- **Scraped docs:** `{"id": "...", "url": "...", "title": "...", "content": "...", "tags": [...], "metadata": {...}}`
- **Stack Exchange:** `{"id": "...", "url": "...", "title": "...", "content": "...", "score": N, "tags": [...]}`

Another AI session is actively expanding the corpus (new scrapers for FreeBSD man pages, Ask Different, MacPorts guide are already landing). The ingestion pipeline must handle new JSONL files dropping in without code changes.

## 3. SourcePrep's Chunker Gap

SourcePrep's build pipeline (`core/index.py:CodeIndex.build()`) classifies files by extension:
- `.md`, `.markdown` → `chunk_markdown()` (heading-based, semantic splitting, min 350 chars)
- `.txt`, `.rst`, `.adoc` → treated as docs, chunked with `chunk_code()` (size-based)
- Everything else → `chunk_code()` (2000 char chunks, 200 char overlap)

JSONL files would be chunked as code — splitting mid-JSON-record, merging multiple docs into one chunk, embedding raw JSON syntax. This is wrong for structured doc corpora.

**Solution:** A JSONL-to-Markdown converter that transforms each JSONL file into a single markdown file with per-doc H2 headings. SourcePrep's `chunk_markdown()` then handles section-based chunking naturally.

## 4. The Roadmap

### Phase 0: SourcePrep Doc Ingestion (the retrieval foundation)

**Goal:** Get 63K+ docs indexed in SourcePrep, retrievable via the existing `SourcePrepRetrievalBackend`.

**0a. JSONL-to-Markdown converter** (~200 lines)
- New file: `halbert_core/halbert_core/rag/jsonl_to_markdown.py`
- Reads any JSONL file, detects schema (man page vs scraped doc vs Q&A), emits markdown
- One markdown file per JSONL source, each doc as an H2 section
- Preserves metadata as HTML comments (`<!-- meta: source_type=man, os=linux -->`)
- Handles all three schemas: `{text, metadata}`, `{id, url, title, content, tags}`, `{id, url, title, content, score, tags}`
- Output to `data/staging/sourceprep/` with directory structure mirroring source:
  ```
  data/staging/sourceprep/
    linux-man-pages/man_pages.md
    linux-arch-wiki/arch_wiki_ext.md
    linux-docker-docs/docker_docs.md
    macos-man-pages/macos_man_pages.md
    macos-homebrew/homebrew.md
    bsd-freebsd-handbook/freebsd_handbook.md
    bsd-freebsd-man-pages/freebsd_man_pages.md
    ...
  ```
- Tests: verify conversion preserves all docs, metadata is captured, heading structure is correct

**0b. Convert the corpus**
- Run the converter across all JSONL files in `data/`
- Verify doc count: markdown H2 headings should match JSONL line counts
- Spot-check a few files for formatting

**0c. Create SourcePrep project and build index**
- Register a SourcePrep project (e.g. "halbert-docs") pointing at `data/staging/sourceprep/`
- Configure `include_globs: ["**/*.md"]`
- Define scopes for platform routing:
  - `linux` → `linux-*/`
  - `macos` → `macos-*/`
  - `bsd` → `bsd-*/`
  - (future: finer scopes like `linux-network`, `macos-storage`)
- Run `prep build` — expect ~10-20 min for 63K docs on M-series
- Verify: test queries ("how to configure sshd", "diskutil apfs", "freebsd network setup") return relevant results

**0d. Wire scopes to retrieval**
- `SourcePrepRetrievalBackend.search()` already maps `figure_id` → `scope`
- Define the scope mapping: intake's `detected_domains` + platform detection → SourcePrep scope
- For now, default to no scope (search all). Scope filtering is an optimization, not a blocker.

**Deliverable:** 63K+ docs retrievable via SourcePrep, accessible through the existing `SourcePrepRetrievalBackend`.

### Phase 1: Intake Pipeline (non-RAG parts, parallel with Phase 0)

**Goal:** Build the message intake module that runs before the cognitive tick.

This phase follows the INTAKE-PIPELINE-DESIGN document exactly, with two adjustments:

**Adjustments from the intake design:**
1. Budget table `self_knowledge` category → absorbed into `memory` and `observations`. The table drops `self_knowledge`; its tokens redistribute. **Note: the intake design doc (§4.5) still lists `self_knowledge` as a budget category — it needs updating to match this decision. The `self_knowledge` ChromaDB collection is being retired in Phase 2c; its contents migrate to SourcePrep observations (rationale/why) and memory_v2 (episodic facts). There is no `self_knowledge` retrieval source after Phase 2.**
2. Budget table `rag` category → rename to `retrieval` (it's SourcePrep now, not ChromaDB RAG). Mark allocations as "v1, needs tuning after Phase 2 lands."
3. **Complexity threshold config home:** the intake design's open question #2 asks whether the 1-2→guide / 3-5→specialist threshold lives in `models.yml` or `being.yml`. Decision: **`models.yml`** — it's a model-routing concern, not a being-preference concern. The being's voice and proactivity dial go in `being.yml` (Phase 6); the complexity threshold is model config.

**1a. `intake/signals.py`** (~200 lines)
- Zero-LLM signal detection: intent, is_question, is_greeting, is_farewell, is_troubleshooting, message_length, detected_domains, has_error_indicators, has_code_blocks, has_file_paths
- No external dependencies, fully testable

**1b. `intake/budget.py`** (~250 lines)
- ModelTier enum (tiny/small/medium/large/xlarge/massive)
- ContextBudget dataclass with per-category allocation
- Budget table (v1, needs empirical tuning)
- `detect_model_tier(model_name)` → tier
- `get_context_budget(model_name)` → ContextBudget
- No VRAM detection in v1

**1c. `intake/complexity.py`** (~200 lines)
- LLM-based complexity router (1-5 scale)
- Uses the guide model (already loaded), 5-token prompt
- LRU cache (100 entries)
- Fast path: greeting/farewell → score=1, skip LLM. Troubleshooting → minimum score=3.
- Fallback: model down → score=3

**1d. `intake/pipeline.py`** (~100 lines)
- `analyze(message)` → chains signals → complexity → budget → `MessageIntake`
- `MessageIntake` dataclass: all fields from the three stages + derived flags (needs_retrieval, needs_tools, needs_web_search)

**1e. Tests**
- `tests/test_intake_signals.py`
- `tests/test_intake_budget.py`
- `tests/test_intake_complexity.py` (mocked LLM)
- `tests/test_intake_pipeline.py` (integration)

**Deliverable:** Standalone intake module, fully tested, no dependency on chat.py or the retrieval backend.

### Phase 2: RAG Consolidation (depends on Phase 0)

**Goal:** SourcePrep becomes the sole retrieval backend. ChromaDB is retired from the chat path.

**2a. Wire SourcePrepRetrievalBackend as sole retrieval in ContextAssembler**
- `context/adapters.py:RAGServiceAdapter` → replace with `SourcePrepRetrievalBackend` (already implements the same `search()` interface)
- Or: add a `SourcePrepAdapter` alongside the existing adapters and set its priority highest
- The `SourcePrepRetrievalBackend` already calls `/context` with `trace_expand=True`, `structured=True`
- **Two wiring points, not one:** `SourcePrepRetrievalBackend` is already wired as the Haloysius `RetrievalBackend` via `integrations/app_seam.py` (the docstring at `sourceprep_retrieval_backend.py:29` confirms the registration pattern). Phase 2a wires it into the *ContextAssembler* (the agent path's context layer) — the Haloysius seam wiring is already done from Phase A–E. Verify both paths route through SourcePrep after this phase.

**2b. Retire ChromaDB from the chat path**
- `context/adapters.py:RAGServiceAdapter` → deprecated, kept for eval only
- `rag/embeddings.py`, `rag/retriever.py` → deprecated on chat path, kept for CLI eval
- `index/chroma_index.py` → `self_knowledge_all` and `self_conversations` collections migrate (2c); `linux_docs` collection is replaced by SourcePrep

**2c. Migrate self_knowledge → memory_v2 + SourcePrep observations**
- `self_knowledge_all` ChromaDB collection → SourcePrep observations (file-anchored, stale-flagged)
- `self_conversations` ChromaDB collection → memory_v2 (Haloysius memory store)
- Migration script: read ChromaDB collections, write to respective stores

**2d. Update ContextAssembler source model**
- Remove `rag` source (replaced by SourcePrep retrieval)
- Remove `self_knowledge` source (replaced by memory + observations)
- Keep: `conversation`, `memory`, `discovery`, `observations`, `system_identity`, `telemetry`, `safety`
- The `SourcePrepRetrievalBackend` handles retrieval; it doesn't need a separate adapter slot if wired as the RetrievalBackend in the app seam

**Deliverable:** One retrieval system (SourcePrep), no ChromaDB on the chat path, clean store ownership.

### Phase 3: Intake Wiring (depends on Phase 1 + Phase 2)

**Goal:** Wire the intake pipeline into the agent path. Skip chat.py entirely.

**3a. Wire into `dashboard/routes/agent.py`**
- Call `intake.pipeline.analyze(message)` before PLANNING state
- Feed `MessageIntake` to:
  - `advance_turn`: intent and complexity_score shape the cognitive tick
  - Context assembler: `context_budget.total` as `max_tokens`, `needs_retrieval` as retrieval gate
  - Model selection: `recommended_model` replaces inline complexity routing
  - Tool routing: `needs_tools` replaces `should_use_tools`

**3b. Wire budget into ContextAssembler**
- `assemble()` gains optional `intake: MessageIntake` parameter
- Uses `intake.context_budget.total` as `max_tokens`
- Per-category budgets from `intake.context_budget` override the flat allocation
- Backward compatible: when `intake` is None, falls back to current behavior

**3c. Do NOT wire into chat.py**
- chat.py keeps its existing scattered intake logic
- It will be retired in Phase 4

**Deliverable:** Agent path uses the intake pipeline. chat.py is untouched and will be retired.

### Phase 4: chat.py Deprecation (depends on Phase 3)

**Goal:** Port chat.py's remaining features to agent.py, then retire chat.py.

This is explorations.md §A1. The agent path is the survivor. Port:
- Telemetry injection → `TelemetryAdapter` (already exists in `extra_adapters.py`)
- Failure correlation → new handler or adapter
- Config-edit blocks → new handler
- Vision (image handling) → new handler or separate flow
- Keyword→discovery injection → replaced by SourcePrep semantic retrieval (already done in Phase 2)

Then retire chat.py endpoint-by-endpoint.

**Deliverable:** One conversation path, one retrieval system, one intake pipeline.

### Phase 4.5: Boot-Test Gate (depends on Phase 4)

**Goal:** Verify the full stack boots end-to-end on the target host. This was flagged as unverified in `the-being.md` §G1 and the foundational research — the agent path with Haloysius + SourcePrep + intake has never been boot-tested together.

**4.5a. Boot test on target host (Ubuntu)**
- `pip install` the full stack: halbert-core + haloysius (external package) + SourcePrep daemon running
- Start the dashboard, verify the agent path responds to a message end-to-end
- Verify: intake runs → context assembled from SourcePrep → cognitive tick fires → LLM responds
- Verify: no ChromaDB dependency on the chat path (collections still exist for eval, but the agent path doesn't touch them)

**4.5b. Boot test on macOS (development host)**
- Same verification, noting macOS-specific gaps (journald unavailable, MLX vs Ollama)
- The being should still work with degraded sensors — "I can't see journald on this body" is an honest answer

**Deliverable:** Confidence that the infrastructure spine works as a whole before building the being layers on top. **This is a hard gate — Phases 5+ don't start until this passes.**

## 5. The Being Layers (Phases 5–8)

Phases 0–4.5 built the spine: one retrieval system, one intake pipeline, one conversation path, boot-verified. Phases 5–8 build the being's signature capabilities — the things that make it more than a chatbot with good retrieval. These map to the two proof slices in `the-being.md` §7 and the explorations in `explorations.md` §C/D/E/H/I.

### Phase 5: The Why Data Model + Config Brain v1 (depends on Phase 4.5)

**Goal:** The being can detect config problems and attach their why to every finding. This is `explorations.md` §C + §E.

**5a. Findings + proposals stores** (`explorations.md` §C1, §C2)
- New: `halbert_core/halbert_core/findings/` — SQLite store for findings (open/snoozed/resolved/dismissed) and proposals (pending/approved/rejected/applied/rolled_back)
- Extends `approval/engine.py` rather than paralleling it — a proposal is an approval request with a finding attached
- Schema as in explorations.md §C1/C2

**5b. Config detectors v1** (`explorations.md` §E1 — pick 3)
- Drop-in conflict (sshd_config.d precedence disagreements)
- fstab phantom (entry references missing UUID/device)
- Permissions hygiene (world-readable private keys, .ssh perms)
- Each detector runs on watch events (`config/watcher.py`) + scheduled sweep + on-ask
- Each detector produces a finding with consequence + evidence refs

**5c. Precedence resolution engine** (`explorations.md` §E2 — minimal)
- sshd_config.d glob ordering + systemd drop-in ordering
- Answers "what is *actually* set?" — required for drop-in conflict detection to avoid false positives
- Also directly useful as a conversation capability ("what's my effective SSH config?")

**5d. Blast-radius (shallow)** (`explorations.md` §E3)
- `config/edge_extractor.py` (Phase 3 work) already extracts direct dependency edges
- For a proposed change: list direct dependents. Deep traversal comes with SourcePrep's graph later.

**5e. Propose-through-approval** (`explorations.md` §E4 — already built)
- `tools/write_config.py` has backup/dry-run/rollback/policy-gate/audit
- `approval/engine.py` + Approvals page exist
- The brain's job is to produce good proposals (C2); the action machinery is done

**Deliverable:** The being can detect a config problem, understand its consequence, compute blast-radius, and propose a fix through the existing approval flow — with every finding carrying its four whys.

### Phase 6: Being Config + Voice (depends on Phase 4.5, parallel with Phase 5)

**Goal:** The user can configure how they live with their computer. This is `explorations.md` §A4 + §H.

**6a. `being.yml` config** (`explorations.md` §H1)
- New: `~/.config/halbert/being.yml`
- Fields: `voice` (first_person/the_computer/hybrid), `proactivity` (off/quiet/balanced/assertive), `category_overrides`, `quiet_hours`, `morning_report` time, `purpose` (free text v1)
- Loaded by the prompt layer (voice) and the proactive gate (proactivity)

**6b. Voice setting** (`explorations.md` §A4)
- `prompts/` PromptBuilder + ContextInjector + AgentPromptBuilder respect the voice setting
- The continuity renderer (Haloysius) renders state blocks in the configured voice
- The self-model and ledger are voice-agnostic; only the expression changes

**6c. Settings UI — "Being" tab** (`explorations.md` §H2)
- `routes/settings.py` gains a `being` section (read/write being.yml)
- Frontend: a new Settings tab with voice picker, proactivity dial, quiet hours, purpose field
- This is the relationship-settings surface — distinct from app config (models) and machine config

**Deliverable:** The user can set voice, proactivity, and purpose; the being's expression changes accordingly.

### Phase 7: The Proactive Channel (depends on Phase 5 + Phase 6)

**Goal:** The being can open the conversation on its own when it finds something worth saying. This is `explorations.md` §D and the proactive half of Slice 1.

**7a. Event flow** (`explorations.md` §D1)
- trigger (watcher event | scheduled sweep | scanner | ingestion anomaly) → detector rule → finding (with four whys) → gate → push to surface + record in ledger

**7b. SSE push transport** (`explorations.md` §D2)
- New: `/api/being/events` SSE stream (server→client push for findings, approvals, morning report)
- The 37-line `websocket.py` stub stays a stub — SSE suffices for v1
- `hooks/useWebSocket.ts` already exists; a `useBeingEvents` hook rides the SSE stream
- POST endpoints for actions: approve/snooze/dismiss

**7c. The gate** (`explorations.md` §D3)
- Severity × category × proactivity dial × quiet hours
- Reads `being.yml` (Phase 6a)
- `autonomy/guardrails.py` already has confidence thresholds + budgets + safe mode — the gate extends it, doesn't replace it

**7d. The morning report** (`explorations.md` §D4)
- Scheduled job: consolidate last 24h (findings, changes, telemetry anomalies, approvals awaiting) into a digest
- Delivered at configured time (being.yml) — the user's first ENGAGED moment of the day
- Uses `scheduler/autonomous_tasks.py` (health check every 6h already exists) + `conversation/summarization.py`

**7e. Ignore semantics** (`explorations.md` §D5)
- Snoozed findings decay back to open after N days if the condition persists
- Dismissed = "user said not a problem" → becomes a rationale entry (SourcePrep concept, §C3)
- The being learns what's noise for this user

**Deliverable:** The being proactively opens the conversation with a config finding, justifies the interruption, and proposes a fix — Slice 1's proactive half, end-to-end.

### Phase 8: The Reactive Slice + Module Invocation (depends on Phase 5 + Phase 6 + Phase 7)

**Goal:** "How are you?" answered as itself, with evidence and a summoned module. This is Slice 2 (`the-being.md` §7) + `explorations.md` §B.

**8a. Provenance refs on claims** (`explorations.md` §C4)
- Every claim in a response can carry provenance refs (log cursor, snapshot id, metric window, path:lines, memory id)
- The LLM expresses intent to cite; the backend validates and attaches real refs (A2 hybrid — never trust the LLM to fabricate evidence)
- UI: the why affordance (§C5) — `WhyChip.tsx`, one component, fed by C1/C2/C3/C4

**8b. Module registry + invocation protocol** (`explorations.md` §B1, §B2)
- Registry: `module_name → { component, data_fetcher, prop_contract, standalone_route }`
- Three invocation paths: LLM-initiated (backend validates), backend-initiated (proactive findings carry their module), user-initiated (palette)
- SSE event vocabulary gains `module_invoke` alongside existing state/response events

**8c. Minimal module set** (`explorations.md` §B4)
- config-diff module (exists: ConfigEditor + DiffBlock)
- drive-health module (storage page subset)
- vitals module (dashboard metrics subset)
- evidence module (log excerpt viewer — new, small)
- Don't refactor all 17 pages up front — curate the rest later

**8d. The reactive slice end-to-end**
- User asks "how are you?" → intake classifies (informational, low complexity) → retrieval fetches biography (recent logs, config changes, self-knowledge via SourcePrep) → cognitive tick renders through continuity in the configured voice → response carries provenance refs → vitals module summons alongside
- Every claim one click from its evidence

**Deliverable:** Slice 2 end-to-end — the being answers "how are you?" as itself, grounded in real data, with evidence and a vitals module.

## 6. Parallelism and Dependencies

```
Phase 0 (SourcePrep ingestion)  ──┐
                                   ├──→ Phase 2 (RAG consolidation) ──┐
Phase 1 (Intake pipeline)       ──┘                                    ├──→ Phase 3 (Intake wiring) ──→ Phase 4 (chat.py retirement) ──→ Phase 4.5 (Boot-test gate)
                                                                        │                                                                                      │
                    Phase 2 depends on Phase 0 (need the index built)   │                                                                                      │
                    Phase 3 depends on Phase 1 + Phase 2                │                                                                                      │
                    Phase 4 depends on Phase 3                          │                                                                                      │
                                                                                                                                                                 ▼
                                                                                                                                    ┌─── Phase 5 (Why data model + config brain) ───┐
                                                                                                                                    │                                                 ├──→ Phase 7 (Proactive channel) ──→ Phase 8 (Reactive slice + modules)
                                                                                                                                    └─── Phase 6 (Being config + voice) ────────────┘
```

**Infrastructure spine (Phases 0–4.5):**
- Phase 0 and Phase 1 run in parallel (no dependencies on each other)
- Phase 2 starts when Phase 0 completes (need the SourcePrep index built)
- Phase 3 starts when both Phase 1 and Phase 2 complete
- Phase 4 starts when Phase 3 completes
- Phase 4.5 (boot-test gate) starts when Phase 4 completes — **hard gate, nothing in Phases 5+ starts until this passes**

**Being layers (Phases 5–8):**
- Phase 5 (why data model + config brain) and Phase 6 (being config + voice) run in parallel after Phase 4.5
- Phase 7 (proactive channel) depends on Phase 5 (needs findings + proposals) + Phase 6 (needs proactivity dial)
- Phase 8 (reactive slice + modules) depends on Phase 5 (needs provenance) + Phase 6 (needs voice) + Phase 7 (needs the push transport)

**The two proof slices land at:**
- **Slice 1 (proactive config worry):** Phase 7 complete — the being detects a config problem and tells you with its why
- **Slice 2 (reactive "how are you"):** Phase 8 complete — the being answers as itself with evidence and a summoned module

## 9. Risks

| Risk | Mitigation |
|------|------------|
| SourcePrep build takes too long for 63K docs | Group per-source (~60 files, not 30K). M-series ONNX embedding is fast. Estimate 10-20 min one-time. |
| SourcePrep chunker doesn't handle man page format well | Man pages have natural section headings (NAME, SYNOPSIS, DESCRIPTION). chunk_markdown() splits on these. Verify in Phase 0d. |
| Budget table allocations are wrong for SourcePrep chunks | Mark as "v1, needs tuning." SourcePrep chunks are richer (trace-expanded) so token density differs. Tune after Phase 2 with observability data. |
| ChromaDB migration loses data | Migration script reads all collections before writing. Keep ChromaDB alive (just off chat path) until migration verified. |

## 10. Open Questions (Non-Blocking)

1. **Should the JSONL converter also handle new scrapers' output?** Yes — the converter is schema-driven, not source-specific. New JSONL files with the same schemas work automatically. New schemas need a converter update.

2. **Should SourcePrep run embedded or as a daemon?** (explorations.md §F3). Current integration uses HTTP daemon. Embedded (library mode) is cleaner for v1 but requires SourcePrep to support library-mode embedding. Defer this decision — the HTTP path works, embedded is an optimization.

3. **Should the intake pipeline run on proactive messages?** (intake design §10.4). When the being initiates (findings, morning report), there's no user message. The pipeline could have a `analyze_self_generated(content_type)` entry point. Defer to post-Phase 3.

4. **Should scopes be auto-derived from directory structure or manually configured?** Start manual (Phase 0c). Auto-derivation is a future optimization.

5. **Haloysius WP-8 predicates — upstream or local?** (explorations.md §G2). The `worries_about`/`conflicted_about`/`wants`/`believes` predicates are planned as WP-8 in Haloysius but not yet implemented. Phase 7 (proactive channel) needs them for worry-as-state. Decision: try upstream first (they belong in the core's ledger vocabulary); fall back to app-seam layer if upstream is slow. The proactive channel works without them initially (findings store carries the state); predicates deepen it.

6. **The intake design's budget table still lists `self_knowledge`** (intake design §4.5). This roadmap's adjustment #1 retires that category. The intake design doc needs updating to match — drop the `self_knowledge` column, redistribute its tokens to `memory` and `observations`. This is a doc reconciliation, not a code change.

7. **Module invocation: LLM-in-band vs backend post-process?** (explorations.md §A2). The hybrid approach (LLM expresses intent, backend validates and attaches real data) is the leaning. Phase 8 needs a concrete protocol design — what structured action does the LLM emit, how does the backend validate it against the module registry, and how does the SSE event carry the payload?

8. **The ambient surface (tray indicator) — when?** (explorations.md §I). The tray indicator is the at-rest mode of the hybrid surface. It's not blocking the slices (the slices work in ENGAGED mode without it), but it's what makes the being feel present when nothing is happening. Suggest: Phase 8.5 or parallel with Phase 8 — the SSE push transport (Phase 7b) already carries the events; the tray is a thin Tauri shell over the same stream.
