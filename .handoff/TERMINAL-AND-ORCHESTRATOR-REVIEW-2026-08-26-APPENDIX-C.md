# Appendix C — design scrutiny (five critics) for TERMINAL-AND-ORCHESTRATOR-REVIEW-2026-08-26

Five parallel adversarial reviews of design v0 (2026-08-26): day-in-the-life admin, terminal interaction, backend/model correctness, accessibility + design system, founder-intent reverse-engineering. Unedited except HTML-unescaping. The v1 design in documentation/design/ folds these in.

# CRITIC: DAY

## SUMMARY
Walked the v0 design through ~20 concrete days as a working admin. The thread/receipt/hint model is sound for the happy path, but the spec is silent on the interactions that happen every day: one-line detours (the design's new_thread is a hard close with immediate compaction + Haloysius write, so a 10-second detour destroys the working set), anaphora after a gap ("so did that work?" has zero signals and an empty hint), wrong recalls (ContextBar's remove handler is a no-op at AgentChat.tsx:650 and the chip is per-turn state), proactive events (today they dead-end in ProactiveEventsBadge with snooze/dismiss only, ContextStage.tsx:45; no thread is named for them), and privacy (no redaction exists anywhere and §4 forbids deletion). Three parts of the spec are unreachable from the code it sits on: §6's long-running-command pool contradicts run_command blocking the turn inside a 30 s default timeout (executor.py:54,411) plus the composer queueing while streaming (AgentChat.tsx:511-515); the watched user shell contradicts the 60 s idle reaper and max_sessions=2 (session_manager.py:42,163-165); and "past turns keep tiles" contradicts "store cleared on reload" plus InlineTerminals dropping unknown sessions (InlineTerminals.tsx:64-66). Multi-window and proactive-during-a-turn both collide with the single global ctx/current_state (state_machine.py:155,214-223). Most fixes stay inside the invariants: add a `paused` thread status with a grace window, make watched-terminal data a compact ledger surfaced through the hint, persist bounded terminal output per turn and render static replays, redact-in-place instead of delete, and give proactive events a paused thread of their own with an indicator light rather than switching the open thread.

## UNCOVERED SCENARIOS
### (a) Mid-Samba, admin asks "what's the date of the last backup?" then says "ok back to the share". Model calls new_thread("Backup date") then new_thread("Samba share setup") next turn.
BREAKS: Per §2.6 new_thread = close old thread -> compaction -> Chroma doc -> Haloysius add_system_event (haloysius_memory_adapter.py:124-150, no delete API). A 10-second detour throws away the Samba thread's last-6 raw turns (the working set); the return trip is a fresh thread whose only Samba context is a receipt the model must recall. Three threads, one dividers-littered timeline, and a first-person episodic memory written for a topic that was not finished. Prompt guidance alone will not stop a small local model from calling new_thread on every subject shift.
HANDLE: Add thread status `paused` (open|paused|closed). new_thread pauses the previous thread instead of closing it; compaction/Chroma/Haloysius happen only when a paused thread ages past a grace window (e.g. 30 min or 5 turns) in the tick. Segmenter rule: if the new turn's signals match a paused thread more strongly than the open one, the server reopens it (no tool call needed) and emits thread_started with reason='resumed'; the divider reads "↩ Samba share setup · resumed". Prompt: "a question you can answer in one reply without tools does not need new_thread". Still exactly one open thread.

### (b) "Fix the Samba share and also why is cron mailing me every hour?" in one message.
BREAKS: Turn -> thread assignment is one thread per turn (§2 step 1). The cron half lives inside the Samba thread; six weeks later "why did cron stop mailing me" runs FTS over thread summaries where cron may be a single sentence, and the Samba receipt is what recall returns. new_thread cannot be called mid-turn for the second half.
HANDLE: Turn stays in the open thread, but the segmenter stores ALL detected domains/entities of the turn on the thread (entities_json is a set, not the title's topic), and the extractive receipt keeps one line per distinct entity cluster. recall_thread returns matching_messages (already in §3) so the cron snippet surfaces even from a Samba-titled thread. Hint text for the next turn: "Thread: 'Samba share setup' · also touched: cron mail".

### (c) Three weeks later the admin opens the app and types "so did that work?"
BREAKS: signals.py:37-66 finds no domain keyword; the past-reference regex list ("we discussed", "last week", "remember when") does not match "did that work"; FTS/Chroma over summaries for "so did that work" scores nothing -> empty hint (§8 says hint failures -> empty hint). The 2h temporal gate fires but §2 never says what it does. The model either answers in a fresh empty thread ("what are you referring to?") or keeps the stale Samba thread open with a 3-week-old last-6 that says nothing about outcome.
HANDLE: Define the temporal gate: gap>2h does NOT open a thread; it changes the hint. When the message has no topic signal, the hint always includes the most recently active thread as the default anaphora target with its receipt's open-loop line: `Most recent: "Samba share setup" (closed Aug 5, 3 weeks ago). Open loop: admin was going to test the share from the laptop after `systemctl restart smbd`.` Add anaphora regex ("that", "it", "did .* work", "any luck", "still") to the past-reference signal. Make the extractive receipt structured: first user message, last assistant message, commands run with exit codes, files written, and a "next step / unresolved" sentence — zero LLM, so (c) is answerable and verifiable ("let me check smbd").

### (d) Hint says strong match on "NAS permissions", model recalls it, answers with the NAS ACL story; the admin says "no, not the NAS, the Samba one".
BREAKS: The wrong receipt is now in the assistant turn's tool block and that turn is inside the last-6 raw turns for the next several turns, so the model keeps seeing it. The ContextBar chip cannot be removed: AgentChat.tsx:650 passes `onRemoveItem={() => {}}`, and the chips are built from `session.contextItems` (AgentChat.tsx:642-651), per-turn state that vanishes on the next message anyway. ContextBar.tsx:14 has no 'thread' type. Nothing tells compaction to drop the retracted recall, so the wrong summary can be baked into this thread's receipt.
HANDLE: Persist recalls on the thread (`recalled_thread_ids` + per-recall status accepted|retracted). Chips are rendered from the thread, not the turn; the X works (DELETE /api/agent/thread/{id}/recall/{tid}) and adds a system-origin observation "admin retracted recall of 'NAS permissions'" that the next PLANNING sees. Chip click scrolls the timeline to that thread's divider. Compaction excludes tool blocks whose recall was retracted. Also let recall_thread return up to 3 candidates when scores are close, so the model can ask "the Jul 14 Samba one or the Jun 30 NAS one?" instead of guessing.

### (e) Admin scrolls up to a turn from three weeks ago (the Samba diff) and wants to answer that turn.
BREAKS: No affordance in §5; the message lands in the open thread and the only link to the old thread is a probabilistic hint. The timeline shows the old turn but nothing on it is actionable except DiffBlock buttons (AgentChat.tsx:695-706) that call /diff/{session_id}/... for a per-turn session that no longer exists (routes/agent.py:932,977 -> 404).
HANDLE: Per-turn "↩ Reply here" action: prefills the composer with a quoted reference and attaches `reply_to_turn_id` to the next /message. Server: hint marks that thread as an explicit strong match and, if the admin confirms via the model's recall (or a one-click "continue this thread" on the quote chip), the server reopens the closed thread and pauses the current one (one open thread preserved, no branching). Timeline stays linear: the new turn appears at the bottom with divider "↩ continuing 'Samba config' (Jul 14)". Past-turn diff/confirmation cards render as static records (applied/rejected/expired), never live buttons.

### (f) Model calls new_thread("Firewall rule for Samba") while the admin is still on the Samba share; a thin divider appears.
BREAKS: The divider is easy to miss and the consequence is invisible: the previous thread's last-6 raw turns left the working context, a receipt was indexed, and a first-person Haloysius line was written that cannot be deleted (adapter has add_system_event only). No merge/undo in the spec. The admin's next message about the share is answered from a receipt instead of from the actual turns.
HANDLE: Divider carries a "merge back ↑" action available for the grace window; merge = reopen previous thread, move the new thread's turns into it, mark the new thread `merged_into`, drop its Chroma doc. Because Haloysius memories cannot be retracted, write the episodic line only when a paused thread ages past the grace window in the tick, never synchronously at new_thread. thread_started carries the model's `reason` so the divider tooltip reads "why: subject changed from share config to firewall".

### (g) Admin pastes a config containing a database password, or in the watched shell runs `mysql -uroot -pS3cret` / `export AWS_SECRET_ACCESS_KEY=...` / `curl -H "Authorization: Bearer ..."`, then wants Halbert to forget it.
BREAKS: §4 says "raw rows never deleted". The secret is now in: SQLite messages + messages_fts (conversation_sqlite.py:83-119), the extractive summary, the Chroma self_conversations doc, the Haloysius episodic line, the opt-in LLM summary, and the bounded terminal-output copy in blocks_json. No redaction code exists anywhere (grep for redact/secret patterns across tools/ and agents/ returns nothing). The watched terminal makes this worse: it captures by design. HybridMemorySystem.forget (memory/hybrid.py:323) only touches the vector store.
HANDLE: Redact-in-place rather than delete: per-turn "forget this" replaces message content and blocks_json with "[redacted by admin]", rewrites the FTS row, regenerates the thread receipt, re-upserts the Chroma doc, and writes a Haloysius retraction event. Inbound scrubber on both the message path and the watched-terminal ledger (password=, -p<token>, Authorization:, AKIA..., PEM blocks, `sudo -S`) before storage. Per-thread `ephemeral` flag ("don't remember this"): kept only in RAM for the working context, never written to SQLite/Chroma/Haloysius; the divider shows it. All opt-in, all inside the invariants.

### (h) Admin, as a human, wants "show me when we touched nginx" and to jump there.
BREAKS: §5 has no search surface; the timeline is newest-50 paged so jumping to a July turn means paging backwards by hand. HostShell.jumpToTerminal (HostShell.tsx:26-31) does a querySelector that silently no-ops when the origin turn is not loaded. FTS5 over messages exists (conversation_sqlite.py:275) but nothing exposes it to the UI.
HANDLE: GET /api/agent/timeline/search?q= (FTS with LIKE fallback) returning hits grouped by thread with dates; a Cmd+F search field above the timeline (not a conversation list — results are turn anchors). GET /api/agent/timeline?around=turn_id so any anchor (search hit, dock ⤴, chip click, notification) can load the surrounding page. Asking the model the same question is also fine: recall_thread with k=3 and an answer listing dates is not a "conversation list".

### (i) In July: "set up Samba for the media box". In September: "how did we do the file share for the windows machine?"
BREAKS: FTS5 over summaries has no synonym knowledge: "file share"/"windows"/"cifs" vs "samba"/"smb.conf". Chroma would help but the HybridMemorySystem vector adapter is broken today (per the verified facts) and §4 only says "fixed". Default FTS5 tokenizer has no stemming, so "mounting" misses "mount".
HANDLE: Alias table at index time in signals.py (smb/cifs/"windows share"/"file share" -> samba; nfs/exports -> nfs; wg/wireguard -> wireguard; certbot/letsencrypt -> tls): thread.entities stores canonical + aliases, and the Chroma doc text is alias-expanded. Create messages_fts with tokenize='porter unicode61'. When the message carries past-reference phrasing, show top-2 candidates even at weak scores so the model can ask.

### (j) At 03:12 the being detects read errors on /dev/sda1 (the-being.md §3 "the channel that opens on its own", §4 Balanced = auto-open for critical). Admin is mid-Samba thread since 22:40, or asleep.
BREAKS: Today the event goes bus -> SSE /api/being/events (being.py:33) -> ProactiveEventsBadge in the ContextStage header (ContextStage.tsx:45) whose only actions are Snooze 7d / Dismiss (ProactiveEventsBadge.tsx:160-170). It never enters the conversation, so it never enters a thread, the timeline, or recall. §2 has no path for a non-user turn, §1 says exactly one open thread, and if it landed in the open Samba thread its receipt would say "we configured Samba and also the disk was failing". If a turn is running, agent.process() cannot be called (single ctx, state_machine.py:214-223).
HANDLE: A proactive event that passes the gate becomes a system-origin turn (messages.origin=system per §4) appended directly to storage (no agent.process) in a NEW thread created `paused`, titled from the finding, category as topic_domain. Timeline renders it in time order with the indicator light on the divider; the tray/critical auto-open scrolls to it but does NOT switch the open thread. The hint block gains a line: `Waiting for you: "Read errors on /dev/sda1" (03:12, critical)`. The admin's reply that references it (or clicks "respond") opens that thread and pauses Samba under the (a) rule. Its first message is the four-whys justification, so Slice 1 lands in the same surface.

### (k) Halbert starts `rsync -a /srv/media /mnt/backup` (12 minutes); the admin moves on to ask about cron; rsync finishes.
BREAKS: This cannot happen with the code the spec sits on: _run_command awaits drain+exit inside the turn under a 30 s default timeout (executor.py:54,366,411), and the composer queues messages while streaming (AgentChat.tsx:511-515, placeholder "Type to queue next message..."). So either the command is killed at 30 s or the admin is stuck watching. §6's pool ("spawn another only when the current one is busy with a long-running command", "long-running -> its own live tile") and the founder's indicator-light + one-click-back describe a background execution model that §7 explicitly defers (task-notification continuation).
HANDLE: Pull a minimal background mode into this spec or cut the pool language: run_command(background=true) returns immediately with the terminal_session_id and a one-line "started"; output flows to the terminal store as today; on exit the server appends an origin=task-notification message to the thread that owns the turn (turn.terminal_session_ids -> thread), persists the bounded output, sets an `unread` flag on that thread, and emits a timeline SSE event. UI: indicator light on the dock row and on the thread's divider (colour + filled/outlined shape); click -> timeline?around=turn -> scrolls to the turn and, per the hint rule, the next message sees `Background command from "Samba share setup" finished 4 min ago: rsync ... exit 0 (12m03s)`. Notify-only; no automatic continuation turn (matches §7's default).

### (l) Backend restarts (crash, upgrade, laptop sleep) while Halbert is mid-turn waiting on a HIGH-risk confirmation, with two agent tiles and one user shell open.
BREAKS: The pending confirmation lives only in agent.active_sessions (state_machine.py:378-382); after restart the Confirm button hits "Session not found". §2.6 appends turns only after response_complete, so the user message of the interrupted turn is never stored — the timeline reloads without it. §5 says the terminal store is cleared on reload and InlineTerminals filters out ids the store does not know (InlineTerminals.tsx:64-66), so every past turn's tiles/chips silently disappear; session_manager.shutdown kills the user shell. reset() also calls terminalSessionStore.clearOrigin (useAgentStream.ts:718-724) from the error banner's retry button (AgentChat.tsx:768-776).
HANDLE: Write the user message at turn start with turn.status=in_progress; finalise on response_complete; a turn still in_progress at boot is marked `interrupted` and renders "(Halbert restarted here)" with confirmation/diff cards shown as expired. Persist bounded output + exit code per terminal session in blocks_json at turn end (and on background exit), and render dead sessions as a static replay tile from the DB — live xterm only for ids present in the store. The error-banner reset must not clear stored turns or their terminal records.

### (m) Admin works in the watched '+ New Terminal' shell for 40 minutes without chatting: `cd`, `vim smb.conf`, `less /var/log/samba/log.smbd`, `ssh nas`, then types "why is the share still read-only?"
BREAKS: TerminalSessionManager reaps any session idle >60 s where activity = stdin or stdout (session_manager.py:42,163-165) — reading a man page for a minute kills the shell, before we even get to 40 minutes. The PTY is raw bytes with stdin via POST /input (terminal.py:330); there is no notion of a command block, exit code, or cwd, so §6's "command blocks flow into the thread" has no source of truth: vim/less emit alt-screen garbage, and everything typed inside `ssh nas` is attributed to this host. If every block is injected as context, 40 minutes of shell flood the working set of a local model whose num_ctx is not set. The existing @terminal "Terminal History" mentionable (discovery.py:93-100) has no backend consumer at all.
HANDLE: Disable the idle reaper for origin=user sessions while a WebSocket client is attached (or TTL in hours). Command-block boundaries require shell integration: spawn the user shell with a PROMPT_COMMAND/precmd hook (OSC 133 A/B/C/D-style markers) that reports command, cwd, exit, duration; skip anything inside alt-screen (1049h) and tag blocks entered inside a foreign `ssh`. Store blocks as a compact per-thread ledger (command, cwd, exit, duration, first/last lines) rather than raw output; the hint says `Since your last message you ran 23 commands in your shell (last: systemctl restart smbd, exit 0, 2 min ago)` and a `terminal_blocks(session_id, n)` fetch (zero-risk tool) gives the model full detail on demand. Watched activity updates thread.last_active for the gap gate but never triggers new_thread. Delete the dead @terminal mentionable or repoint it at the ledger.

### (n) Admin has the desktop app open on the workstation and the web dashboard on a laptop; sends from both within a minute.
BREAKS: One global self.ctx and self.current_state (state_machine.py:155,214-223); the force-reset guard in routes/agent.py:659-668 only matches the same session_id, which never happens because useAgentStream mints a new id per message (useAgentStream.ts:523). The second process() overwrites ctx mid-turn and both streams get garbage. Each window sees only its own SSE; window B never learns that window A appended a turn or that a thread was opened.
HANDLE: Serialize turns server-side (asyncio.Lock around process(); a second caller gets 409 with the running turn's id, or is queued). Add one persistent timeline SSE (`/api/agent/timeline/events`: turn_appended, thread_started, thread_recalled, task_notification) that every window subscribes to; this is the same channel (j) and (k) need.

### (o) Marcus (compliance persona) needs to hand the "SSH hardening" thread to a colleague / attach it to a ticket / print it.
BREAKS: Nothing in §1-§9 exports a thread; copying from the timeline loses tool cards, diff results, and terminal output; redactions from (g) are not guaranteed to apply to whatever is copied.
HANDLE: GET /api/agent/thread/{id}/export?format=md producing turns, tool cards (name/args/exit), applied diffs, and trimmed terminal blocks, with the same redaction applied; a "copy/export" item on the divider. Low effort once blocks_json exists.

### (p) End-to-end: Jul 14 the admin and Halbert added a [media] share; six weeks later: "I want to add another share for the scanner, same as we did for the media one."
BREAKS: With today's keyword lists "share"/"samba" are not domain keywords (signals.py:37-66), so the only signal is FTS/Chroma over summaries for "share scanner media"; the hint depends entirely on the Jul 14 receipt containing "media share". build_planning_prompt takes only query/context/plan/observations (agent_prompts.py:194-199) so the hint has to ride inside `context` or masquerade as an observation. The chip built from session.contextItems disappears on the next turn (AgentChat.tsx:642-651). Recall costs an extra PLANNING->OBSERVING->PLANNING loop on a local model.
HANDLE: Hint (top of PLANNING context, own section): `<continuity>\nThread: "Scanner share" · 1 turn · opened just now.\nEarlier threads that may matter:\n- "Samba media share" (Jul 14, 6 weeks ago, strong match: samba, smb.conf, media share) — outcome: [media] share added, smbd restarted, admin confirmed access from laptop.\n- "NAS permissions" (Jun 30, weak).\nThe admin refers to earlier work; call recall_thread before answering.\n</continuity>`. Tool call: `recall_thread({"thread_id": "thr_2026-07-14_samba"})`. Result: `{"title":"Samba media share","date":"2026-07-14","summary":"Added [media] to /etc/samba/smb.conf: path=/srv/media, browseable=yes, guest ok=no, valid users=eric, create mask=0664. Ran testparm (exit 0), systemctl restart smbd (exit 0). Admin confirmed mount from laptop.","commands":[{"cmd":"testparm","exit":0},{"cmd":"systemctl restart smbd","exit":0}],"files_written":["/etc/samba/smb.conf"],"matching_messages":["...[media] path = /srv/media..."]}`. SSE thread_recalled -> thread-level chip `↺ Samba media share · Jul 14` (click scrolls to that divider; X retracts). Admin sees: chip; answer "On Jul 14 we added [media] with path=/srv/media, guest ok=no, valid users=eric. I'll add [scanner] the same way at /srv/scanner" + a DiffBlock for smb.conf + the testparm tile. Requires: samba/smb/cifs/share aliases in signals.py, hint as a first-class prompt section, chips persisted on the thread.

### A HIGH-risk command is awaiting confirmation (AWAITING_CONFIRMATION keeps the session parked, state_machine.py:262-264) and the admin types something else; the model calls new_thread.
BREAKS: The parked session leaks in active_sessions; the closed thread's receipt records a command that was never run or refused; §8 says nothing about pending confirmations at thread close.
HANDLE: Closing or pausing a thread auto-rejects its pending confirmation (same path as confirm_action(confirmed=False) at state_machine.py:399-415) and records "not run — superseded" in the receipt; the timeline card shows expired.

### The first thread of the day has no name: §2 step 1 "open one if none" is zero-LLM, but the divider shows `title · relative date` and new_thread(title) is only called on change.
BREAKS: Dividers read "Untitled · just now" for the most common case; recall hints list untitled candidates.

### Reload after a long day: timeline pages 50 turns each with tool cards and terminal tiles; three past turns had live tiles.
BREAKS: MAX_VISIBLE=3 xterm instances (useTerminalSessions.ts:69) plus one-xterm-per-session means paging history mounts/unmounts tiles constantly; the observer guard in §6 covers flicker but not the cost of reviving 50 turns' tiles, and dead sessions have no store entry so they render nothing (InlineTerminals.tsx:64-66).
HANDLE: Static replay tiles for stored (dead) sessions from blocks_json — a styled <pre> with exit/timing, not xterm; xterm only for live ids. Then MAX_VISIBLE only governs live terminals and history pages are cheap.

## CONTRADICTIONS
### §6 terminal model (agent pool reuses an idle session, spawns another when busy with a long-running command, long-running -> live tile) vs §7 deferral of task-notification continuation vs current executor
run_command blocks the turn until exit under a 30 s default timeout (executor.py:54,366,411) and the composer queues input while a turn streams (AgentChat.tsx:511-515). There is no turn in which a command is "long-running" while the admin does anything else, so the pool, the indicator light, and one-click-back have nothing to attach to.
RESOLVE: Either add background=true to run_command in this spec (completion -> origin=task-notification message + unread flag, notify-only) or rewrite §6 to "commands complete within the turn; reuse is a per-turn PTY for successive short commands" and move pool/indicator to §7.

### §4 "raw rows never deleted" vs privacy/forget (scene g) and vs Haloysius write-on-close
Secrets pasted in chat or typed in the watched shell are copied into five stores with no redaction anywhere (no redact/secret-pattern code in tools/ or agents/); Haloysius has add_system_event only (haloysius_memory_adapter.py:124-150).
RESOLVE: Keep rows but allow redact-in-place with derived-store regeneration; scrub inbound; defer the Haloysius write to the tick after the grace window; add an ephemeral thread flag.

### §5 "terminals persist per turn so past turns keep tiles/chips; store cleared only on reload" vs §1 "timeline = every turn forever"
After any reload the store is empty and InlineTerminals drops ids it cannot find (InlineTerminals.tsx:64-66), so every historical turn loses its terminal evidence; dock ⤴ no-ops for unloaded origins (HostShell.tsx:26-31).
RESOLVE: Persist bounded output/exit per session in blocks_json; render static replay tiles from the DB; add timeline?around= for anchors.

### §1 "exactly one open thread" vs the-being.md §3/§4 proactive channel that opens on its own (and §7 child threads)
A proactive finding at 03:00 has no thread to land in; if it opens a thread it breaks the invariant, if it lands in the open thread it poisons that receipt; today it never reaches the conversation at all (ProactiveEventsBadge.tsx:160-170 snooze/dismiss only).
RESOLVE: Introduce `paused` status: proactive events create a paused thread with a system-origin turn; only an admin reply opens it. Same status serves asides (a), merges (f), and sub-agent children later.

### §2 "hint block at top of PLANNING context; history = compacted_summary + last 6 raw turns" vs the existing context assembler
build_planning_prompt has no hint slot (agent_prompts.py:194-199); ContextAssembler._format_conversation already does last-6 + extractive summarisation (assembler.py:349-370) and budgets conversation at 10-25% of context_budget (assembler.py:277-292). Passing a summary message plus 6 turns into a path that summarises again yields double summaries and the hint competes with them inside the same budget.
RESOLVE: Make the hint a first-class prompt section (build_planning_prompt(hint=...)) with its own reserved budget; pass the thread's history pre-compacted and disable the assembler's second compression for the agent path.

### §6 "user shell kept and watched" + "agent owns a small pool" vs TerminalSessionManager limits
max_sessions=2 and idle_ttl 60 s (session_manager.py:42,65-68,163-165). One user shell + one agent session hits capacity; "spawn another when busy" raises AtCapacityError; an admin reading output for a minute loses the shell.
RESOLVE: Raise max_sessions, separate caps per origin, and suspend the idle reaper for user sessions with an attached client.

### §5 "server owns thread identity" vs cancel/confirm/diff keyed on per-turn session ids (routes/agent.py:725,785,932,977) and the visible `Session: xxxxxxxx…` footer (AgentChat.tsx:893)
Rendered past turns carry DiffBlock/confirmation buttons bound to dead session ids -> 404s; the footer exposes an id that means nothing to the admin.
RESOLVE: Render stored turns' actionable cards as static records; keep per-turn keying only for the live turn; replace the footer with the thread title.

### §2.6 "after response_complete: append user+assistant turns" vs §8 "store failures never block a turn" and scene (l)
A cancelled, errored, or crashed turn never reaches response_complete, so the user message is not stored and the timeline forgets the admin asked.
RESOLVE: Store the user message at turn start with status in_progress; finalise or mark interrupted/cancelled.

### §3 "Ctrl/Cmd+N in composer = explicit new thread" vs desktop conventions
Cmd+N is New Window in Tauri/macOS and the composer's handleKeyDown only handles Enter/Escape (AgentChat.tsx:541-548).
RESOLVE: Use a slash command or Cmd+Shift+N; keep new_thread visible via a divider preview before send.

WHY: Without it, a one-line detour, a proactive event, or a mistaken new_thread destroys the working set and writes irreversible memory (Haloysius has no delete).

# CRITIC: TERMINAL

## SUMMARY
§6 describes command *blocks* with origin/exit/timings/cwd inside PTY *sessions*, but nothing in the codebase produces block boundaries: the user shell is a raw `/bin/sh -c 'exec $SHELL -i'` PTY (TerminalAccordionDock.tsx:43, routes/terminal.py:306-313) with no OSC 133 / precmd / PROMPT_COMMAND / rcfile injection anywhere (grep across streaming/, routes/, hooks/ returns nothing), and agent commands are one-shot pipes (executor.py:376-381) that never touch a PTY. Every §6 promise — watched user shell, reused agent session, hidden-until-long-running, tidy dock of sessions-with-blocks — sits on a shell-integration layer and a block store that do not exist and are not named in §4 or §9. Beyond that gap, the current substrate actively fights the design: TerminalSessionManager caps at 2 sessions and reaps anything with no stdin/stdout for 60 s (session_manager.py:42,157-165) — that kills the "idle agent shell" the founder wants reused, and today already kills a user's attached-but-quiet shell; PTYSession.read_chunk registers a per-consumer add_reader on one fd (pty.py:176-197) so a second consumer (WS reattach, SSE /stream, an agent watcher) silently starves the first; WS attach never replays `get_buffer()` (websocket.py:73-83); the frontend never GETs /api/terminal/sessions, so a reload empties the dock even while PTYs live; the user's "+ New Terminal" shell is wrapped by the *agent* sandbox (routes/terminal.py:306-307 -> sandbox.py:153-158 denies writes under /etc, /usr, /Library; bwrap on Linux gives it a read-only root and a private /tmp with no writable_paths), while the agent's own run_command is unsandboxed (`"sandboxed": False`, executor.py:381) — the opposite of "terminal generally owned by the agent". The spec needs a concrete shell-integration + block model, a rewritten session-manager policy (kinds, TTLs, pool), a fan-out-safe PTY reader, a bounded/redacted block record with an `origin=terminal` message row so the agent can see and later recall "the admin ran smbstatus, exit 1", and explicit rules for interactive/alt-screen programs. Several of those are "this spec"; tabs and stdin-capable agent commands stay "next".

## UNCOVERED SCENARIOS
### User opens '+ New Terminal', runs `smbstatus`, reads the output for 90 s without typing, then types the next command.
BREAKS: The shell is already dead. `_reap_once` uses max(stdin touch, last_output_at) and kills at idle > 60 s (session_manager.py:157-165); WS only touches on client messages (websocket.py:98) and on pump_stdout exit (websocket.py:86). A quiet shell with a WS attached is 'idle'. The frontend marks it done with exit -1 on socket close (useTerminalSessions.ts:235-241). A watched user terminal that dies after a minute of reading cannot be watched.
HANDLE: Give sessions a `kind` (user | agent-pool | oneshot) and per-kind policy in TerminalSessionManager: user sessions are never idle-reaped while any WS is attached (track attach count; touch on attach/detach) and get a long detached TTL (e.g. 30 min, configurable); agent-pool sessions get a pool TTL (e.g. 15 min) and are never reaped mid-block; only oneshot sessions keep the 60 s rule. Name this in §6 and §4.

### Agent runs `df -h` then, 10 s later in the same turn, `ls /srv/samba` via a reused pool shell; the tile is mounted inline (attach 'ws') and the user clicks into it and presses Enter while the second command runs.
BREAKS: TerminalTile treats every 'ws' session as interactive (TerminalTile.tsx:46,86-87,105-107) and forwards keystrokes to the PTY; the user's stray input lands in the agent's shell mid-command and corrupts the block stream the boundary parser is reading. There is no ownership concept in the store (useTerminalSessions.ts:36-51 has no owner field).
HANDLE: Add `owner: 'user' | 'agent'` to TerminalSession and the spawn/attach events; agent-owned sessions mount with disableStdin and no cursor unless the user explicitly 'takes over' (a button that flips owner to user and marks the session foreign so the pool never writes to it again). Put this in §6 under the pool rules.

### Agent needs a second concurrent command while the pool shell is busy with `rsync` (long-running); the user also has one shell open.
BREAKS: TerminalSessionManager default max_sessions=2 (session_manager.py:42) and nothing configures it (grep for max_sessions/idle_ttl outside the module: none). User shell + busy pool shell = 2; the next spawn raises AtCapacityError → 503 (routes/terminal.py:255,314). The legacy /terminal page also burns a PTY per one-shot command through /api/terminal/exec (pages/Terminal.tsx:209, lib/api.ts:342), competing for the same cap.
HANDLE: Raise the cap and make it per-kind (e.g. user ≤ 3, agent-pool ≤ 3, oneshot ≤ 2) from config; when the pool is at cap and all busy, the executor falls back to the current subprocess path rather than failing the tool. Retire /api/terminal/exec from the frontend (or exempt oneshot from the interactive cap).

### Long-running `tail -f /var/log/samba/log.smbd` in a reused pool shell hits the run_command timeout (DEFAULT_TIMEOUT 30 s, executor.py:54,366).
BREAKS: Today the tool kills the child process (executor.py:456-459). With a persistent shell there is no `proc` to kill; killing the session throws away the pool shell and any cwd/env state; not killing leaves the block open forever and the session permanently 'busy'.
HANDLE: Timeout on a pool block = write ETX (\x03) to the PTY (tty delivers SIGINT to the foreground pgrp), wait up to a grace period for the 133;D marker; if no D arrives, kill the session, drop it from the pool, and emit terminal_complete exit -1. Run the agent pool shell with job control on (`set -m`) so each block is its own process group. Spell this out in §6 as the replacement for kill semantics.

### Backend restarts (or the machine sleeps and the daemon is relaunched) while a user shell and a pool shell exist; the timeline is stored in SQLite.
BREAKS: PTY children are forked from the daemon (pty.py:121) and die with it; the manager singleton is recreated empty (session_manager.py:176-184). The stored turn still lists terminal_session_ids (§4 messages.terminal_session_ids) with status running; the frontend store is in-memory only and never calls GET /api/terminal/sessions (only POST at useTerminalSessions.ts:107), so after a reload the dock is empty and every stored chip points at a session that 404s on /ws/terminal/{id} (websocket.py:65-68).
HANDLE: On frontend mount: GET /api/terminal/sessions, `attach()` each live id, and mark any stored block/session ids not in that list as `ended: unknown` (render frozen from the stored bounded output, no ⤴ live target). On backend startup: mark all blocks with ended IS NULL as `exit=null, status='lost'`. Add both to §8.

### User's WS drops (laptop lid) and reattaches to the same session id 20 s later, or two components attach to one session (inline tile + expanded dock row).
BREAKS: Reattach: pump_stdout starts a fresh read_chunk and never sends `session.get_buffer()` (websocket.py:73-83), so the reattached xterm is blank. Two consumers: each read_chunk registers its own `loop.add_reader(master_fd, …)` (pty.py:174-197); asyncio replaces the callback for an fd already registered, so only the newest consumer receives bytes and the older one hangs on `queue.get()`; when the newer one finishes, its `finally` calls remove_reader and the older one is dead too. Any backend-side watcher (the block parser) plus the WS bridge is exactly this two-consumer case.
HANDLE: Refactor PTYSession to a single reader task that fans out to all `_read_queues` (the set already exists at pty.py:79 but is only used by kill()); on WS attach send a `{type:'replay', data:get_buffer()}` before live chunks; make the frontend `attach()` reset `output` from the replay instead of appending. This is a hard prerequisite for a watched shell.

### The `+ New Terminal` shell is used by the admin to edit `/etc/samba/smb.conf` with `sudo vi` on macOS, or to `git clone` into $HOME on a Linux box with bwrap installed.
BREAKS: spawn_session wraps the shell in Sandbox (routes/terminal.py:306-307). macOS profile denies file-write* under /etc, /usr, /System, /Library, /private/etc, /var/db (sandbox.py:153-158) for the whole shell and all children, so the edit fails after the password prompt. On Linux `_wrap_bwrap` mounts / read-only with tmpfs /tmp and /run and no writable binds because `spawn(NEW_SHELL_COMMAND)` passes no writable_paths (TerminalAccordionDock.tsx:87) — the admin's shell cannot write its own home. Meanwhile the agent's run_command runs with no sandbox at all (executor.py:376-381, sandboxed False).
HANDLE: The user shell is the admin's shell: spawn it unsandboxed (kind=user). Apply the sandbox to agent-pool shells at spawn with writable_paths derived from policy. State this inversion explicitly in §6; today the spec is silent and inherits the wrong default.

### Admin runs `vim smb.conf`, `less`, `htop`, or `sudo` (password prompt) in the watched shell; or the agent's pool command triggers a sudo prompt.
BREAKS: With OSC 133 hooks, preexec emits C but D never arrives until the program exits: the block stays open (correct: session is busy) but the 'bounded output copy' fills with alt-screen escape soup that is useless to the model and to recall. For the agent pool, a sudo prompt blocks the shell until the tool timeout; nothing detects it, the model sees nothing, and the block is reported as timed out.
HANDLE: In the boundary parser: on `\x1b[?1049h` / `\x1b[?47h` set block.interactive=true and stop copying output (record only command, start, end, exit); clear on `\x1b[?1049l`. Agent pool shells export `SUDO_ASKPASS=/bin/false` and the <continuity>/tool prompt says to use `sudo -n`; the parser flags a block whose tail matches a password-prompt regex with no output for N s as `needs_input` and emits a terminal_needs_input SSE (surfacing as the tool card state) — stdin routing for the agent stays 'next'.

### Admin runs `export AWS_SECRET_ACCESS_KEY=…` or `mysql -p'hunter2'` in the watched shell; later a recall pulls the thread receipt into the model context and the Chroma self_conversations doc.
BREAKS: The command line is echoed by the tty and captured in the block; §6 says nothing about redaction, so the secret is written to SQLite (FTS5-indexed), to the thread summary, and possibly to Chroma and Haloysius memories.json — durable and searchable.
HANDLE: A `streaming/redact.py` pass over block.command and block.output before storage (key/token/password= patterns, `-p<...>`, bearer tokens, PEM blocks), plus a per-block `redacted: true` marker; passwords typed at a no-echo prompt never enter the stream. Also add a user-visible per-session 'not watched' toggle (Warp-style privacy) which suppresses block export entirely.

### Agent ran `rsync` as a long-running block two turns ago (tile mounted inline in that turn); it finishes while the user is in the Layout's browsing mode looking at Files.
BREAKS: §6's indicator light has no owner element or clearing rule. The only origin anchor is `data-terminal-origin={session.id}` (InlineTerminals.tsx:46) and the jump helper matches by session id (HostShell.tsx:26-31); with block-level tiles and reused sessions, one session id maps to several turns, so 'jump to origin' is ambiguous. If the thread is closed, do NOT recall it into the open thread — just scroll to its divider; recall stays a model tool.

### A block emits 4 MB of output in 2 s (e.g. `cat` a log) in a pool shell while the tile is live.
BREAKS: TerminalEventBus drops oldest payloads at 512 items (terminal_bridge.py:47,96-104); if the block copy is derived from bus payloads, the stored output has holes and may lose the `complete` for a fast-succeeding block. ## CONTRADICTIONS
### §6 'inline tile lives inside its ToolExecutionCard; one xterm per session' vs 'terminals persist per turn so past turns keep tiles' (§5) and 'reuse an idle agent session'
If one session is reused across turns 3, 5 and 7, three ToolExecutionCards claim the same session's single xterm. useTerminalSessions is session-keyed with a per-session `visible` flag (useTerminalSessions.ts:36-51,314-329), and TerminalTile writes the whole session stream from writtenRef=0 on mount (TerminalTile.tsx:138-159) — the turn-3 tile would show turn-7's output.
RESOLVE: Tile = block. Only the session's *current open* block may own the live xterm; every completed block renders a frozen <pre> from its bounded output copy (no xterm, no socket). Add `blocks[]` and `currentBlockId` to the store; MAX_VISIBLE=3 then caps live xterms across sessions with open long-running blocks, which is the right thing.

### §6 'hidden-until-long-running: short commands show a one-line result' vs current SSE pipeline and 'busy' semantics
Today the tile spawns on `terminal_spawn` before any output (executor.py:376-386; useAgentStream.ts:182-197). There is no elapsed-based promotion, and 'long-running' and 'busy' are conflated in the spec: a pool session is busy the instant a block opens, but the tile should only appear after N s.
RESOLVE: Define both: busy = block open (133;C seen, no 133;D); long-running = block open for > 2 s (backend emits `terminal_block_promote`; frontend may also promote on its own timer). Reuse decision uses busy; UI uses long-running.

### §6 'User shell is the same thing with origin=user' vs §4 messages.origin enum (human|assistant|task-notification|system)
Watched-shell blocks must land in the thread as citeable rows for FTS5 recall, but no origin value exists for them; stuffing them into `system` makes them indistinguishable from thread_store_error notices, and stuffing them into the hint only makes them unrecallable later.
RESOLVE: Add origin='terminal' to §4; content_to_text = '$ <cmd>\n[exit N, 0.3 s, cwd]\n<tail ≤ 20 lines>'; blocks_json = {block_id, session_id, owner, cwd, exit, started, ended, interactive, redacted}. Full bounded copy lives in a `terminal_blocks` table keyed by block_id, referenced from the row.

### §6 'Out of scope: PTY-backed agent commands with stdin/sudo (attach:"ws" seam exists)' vs 'reuse an idle agent session'
Reuse *is* a PTY-backed agent command: the pool shell is a PTY session in TerminalSessionManager and the tile must attach with 'ws' to see it live (or a new fan-out path). You cannot have reuse without crossing the line the spec draws. What is genuinely deferrable is the user typing into the agent's PTY, not the PTY itself.
RESOLVE: Reword: in scope = agent commands executed in a PTY pool session with stdin closed to the user (owner=agent, disableStdin) and ETX-based timeout; next = user take-over / password entry into agent sessions.

### Founder 'terminal is generally owned by the agent' vs routes/terminal.py + sandbox.py
The user shell is sandboxed (routes/terminal.py:306-307), the agent's commands are not (executor.py:381 sandboxed False). The spec's safety story assumes the reverse.
RESOLVE: Spawn user shells unsandboxed; sandbox agent-pool shells at spawn (persistent wrapper, so writable_paths cannot vary per block — the spec must accept per-session rather than per-command sandbox policy, or drop the sandbox on the pool shell and rely on ToolSafetyFramework gating at safety.py:288-415, which already runs before the executor).

### §5 'jump ⤴ always has a target' / §6 'one click surfaces the associated hidden thread' vs paged timeline (§5 newest 50 turns)
HostShell.jumpToTerminal is a querySelector over rendered DOM (HostShell.tsx:26-31). A block from a turn older than the loaded page has no DOM node; the click silently does nothing.
RESOLVE: Timeline endpoint takes `around=<turn_id>`; the click handler loads that page first, then scrolls to `[data-terminal-block=…]`.

# CRITIC: A11Y

## SUMMARY
The v0 design's accessibility story is one sentence ("colour + fill/outline") on top of a component layer that today has zero aria-live regions, colour-only status dots, div-with-onClick rows, unlabeled glyph buttons, Tailwind pulses that ignore the reduced-motion gate, and a right column that unmounts entirely below 768px (taking the dock, the bell and every terminal with it). The indicator light needs a full state table (5 states, token per state, a non-colour channel drawn as SVG so it survives forced-colours, one polite status region, assertive only for blocked-on-approval, and NO idle pulse -- brand §5 forbids it; use a single 220ms token-timed blink on transition). Thread dividers should be headings with <time>, not separators, so screen-reader H-nav and the planned J/K nav share one structure; recalled chips are telemetry-tone provenance and must be real buttons. Live xterm tiles need a focus escape hatch and a guarded global Ctrl+B (today ShellModeContext.tsx:80 hijacks the tmux prefix inside a user PTY); the new Ctrl/Cmd+N must be composer-scoped. No new colour token is required if the light only ever sits on canvas/surface; one Tailwind alias gap (status-*-line) and one ratchet gap (bg-[#hex]) need closing. Timeline paging must render closed-thread turns as receipts, not re-hydrated tool cards, and dividers need absolute dates past 48h.

# CRITIC: INTENT

## SUMMARY
The design honours the founder's headline (one timeline, no conversation list, hidden threads, watched user shell, agent terminal reuse, subtle indicator light) at the storage and pipeline level, but leaks the "hidden" sessions back into the UI in three places (titled topic dividers, a 'thread' ContextBar chip, Ctrl/Cmd+N manual thread control) and makes the two behaviours the founder actually asked for — "pull that context back" and "context does not bleed on topic change" — depend entirely on a local model choosing to call recall_thread / new_thread, whereas the corpus (FEASIBILITY §4:120-122, CONTINUOUS §4 step 3) and the recorded founder direction ("re-anchor = thread summary pulled into context") auto-rehydrate on a strong match. Section 6 contradicts itself: an agent terminal pool with reuse cannot be built on today's one-process-per-command `create_subprocess_shell` (executor.py:375) while "PTY-backed agent commands" are out of scope, and the watched user shell has no mechanism for command-block boundaries on a raw login-shell PTY (pty.py) — without shell integration the founder's "know what you entered and can see the results" is a byte stream. The design also forgets the founder-decided proactive channel/morning report (the-being.md §3-4, already scheduled in app.py:426-445, currently a bell popover in ContextStage.tsx:45) which has no origin or thread semantics in the timeline; forgets WhyChip provenance on recalled context; adds a new production Chroma collection despite "ChromaDB stays for eval only" (the-being.md §9) and "no third memory store" (explorations §10); and gives the admin no cue-before-the-fact or "no, same topic" recovery when new_thread drops the last turns. The founder's wording implies the watched shell is read-only for the agent; the design should say so explicitly and must add secret redaction before persisting shell blocks forever ("raw rows never deleted").

## UNCOVERED SCENARIOS
### Local model never calls new_thread when the admin moves from Samba to ZFS (small Ollama models are unreliable at optional tool calls; the design's zero-LLM domain signals in §2 step 2 are computed but never act on a boundary).
BREAKS: Founder purpose #2 ('lingering context does not bleed on topic change') fails silently: the last 6 raw Samba turns plus the Samba compacted summary go into the ZFS turn's context (§1 working context). FEASIBILITY §2:59 specified a deterministic Topic Boundary Gate; the design has none.
HANDLE: Feed the existing intake domain signal (intake/signals.py:37-73, analyze_message :155) into the hint: when detected_domains are disjoint from thread.topic_domains and there is no entity overlap for 2 consecutive turns, the hint says 'subject appears to have changed (storage -> network); call new_thread unless continuing', and if the model still does not call it, the assembler drops the raw turns to summary-only for that turn (soft boundary) — deterministic, zero-LLM, matches FEASIBILITY §2/§4.

### Model calls new_thread spuriously mid-task ('now check the smb.conf permissions' read as a new topic). The old thread is closed, compacted, indexed, and a Haloysius episodic line is written (§2 step 6) before the admin has seen the response.
BREAKS: Next turn the model has lost the last 3 raw turns; the admin sees a titled divider appear after their message and the assistant 'forgets'. There is no undo: status is open|closed only, recall_thread returns a receipt (summary + <=5 snippets) never the raw turns, so a wrong split permanently degrades working context even though raw rows survive in SQLite. Ctrl/Cmd+N only goes the other direction. the-being.md §1 item 6 requires 'actions have visible outcomes ... how to undo'.
HANDLE: (a) Grace window: for the first turn after a split keep the previous thread's last 3 raw turns in context. (b) Make close lazy: compaction/Chroma/Haloysius side effects run only once the new thread survives >=2 turns or the day closes. (c) A one-click 'same topic' on the divider (or the model on user objection) reopens the previous thread and marks the new one merged. ### Interleaving within minutes: Samba -> ZFS -> back to Samba. §1 says exactly one open thread and status is open|closed; nothing reopens a closed thread.
BREAKS: Three threads ('Samba share setup', 'ZFS scrub', 'Samba share setup (2)'), two Chroma docs and two first-person Haloysius memories for one task; later hints list two Samba threads; the founder's 'multi-task secondary' foreseen failure mode becomes a memory-pollution failure mode.
HANDLE: On strong match to a thread closed within 24h, reopen it instead of creating a new one (status open|closed|merged); emit the Haloysius episodic line only for threads with >=N turns or at day close, never per close.

### Admin waits 2h05 for a zpool scrub the agent started, then says 'ok, it finished — what did it find?'. The 2h temporal gate (§2 step 2, inherited from FEASIBILITY §2:58) closes the thread.
BREAKS: Same-task resume loses the raw turns (only compacted summary + hint 'strong match'), the terminal session ids of the scrub tile are now in a closed thread's receipt, and unless the model calls recall_thread the answer is built from an extractive summary. The founder's example was 6 weeks, not 2 hours; long waits are the normal sysadmin rhythm.
HANDLE: The temporal gate marks the thread stale and adds 'resuming after 2h' to the hint, it does not close; close only on (gap AND domain shift) or an explicit new_thread. Live terminal sessions spawned by a thread keep it open.

### Watched user shell: '+ New Terminal' is a raw login shell on os.openpty (streaming/pty.py:113-160, TerminalAccordionDock.tsx:41-87 spawns $SHELL). §6 promises command blocks with command, exit code, cwd, bounded output.
BREAKS: There is no command boundary in a raw PTY byte stream: tab completion, prompts, vim/top/less, multi-line heredocs and ANSI redraws all become one undifferentiated buffer. The founder's 'know what you entered and can see the results' cannot be derived; the agent would cite prompt garbage as a 'result'.

### Admin types `export HF_TOKEN=hf_...`, `mysql -u root -pSecret`, or pastes an SSH key into the watched shell. §6 flows blocks into the thread; §4 'raw rows never deleted'; §2 step 6 compacts into Chroma self_conversations and a Haloysius memory; §7 later exposes memory tools.
BREAKS: Secrets are persisted forever in three stores and can be regurgitated by recall_thread or a future proactive message. This is a new privacy exposure the watched-terminal decision creates; nothing in §8 covers it.
HANDLE: Redaction pass on origin=user blocks before persistence (known patterns: -p<pw>, token=, Authorization:, BEGIN PRIVATE KEY, AWS/HF/GitHub key shapes); store bounded output only; never forward user-shell blocks to Haloysius/Chroma, only to the thread's raw rows and extractive summary; per-session 'unwatched' toggle on the dock row.

### Agent pool reuse (§6: 'reuse an idle agent session for successive short commands'). run_command today is one asyncio.create_subprocess_shell per call (tools/executor.py:375, attach:'sse' at :392) — there is no process to reuse — and §6 declares PTY-backed agent commands out of scope.
BREAKS: Reuse requires a persistent shell process, which makes the agent's commands stateful: `cd /etc` in block 1 changes block 2's cwd, `export`/`set -e`/background jobs leak, a pager (`less`, `git log`) or a `read` leaves the session 'busy' forever so the pool keeps spawning. ## CONTRADICTIONS
### Design §2 step 3/§3 ('Explicit references do not silently rehydrate; hint marks strong match and prompt tells the model to recall') vs FEASIBILITY-AND-ENGINEERING-REALITIES.md §4:118-122 ('if matched_session.score > 0.80: seamlessly load the past session's compacted summary'), CONTINUOUS-ORCHESTRATOR §4 step 3 lines 124-127 (high match auto-rehydrates), and the recorded founder direction in memory/halbert-continuity-direction-2026-08-26.md ('Prefer re-anchor behaviour — thread summary pulled into context')
Both corpus docs and the founder note make a strong match deterministic: the summary is pulled into context by the assembler. The design downgrades this to a title-only hint plus a model-initiated tool call, so 'halbert remembers ... and can pull that context back' depends on a local model electing to call recall_thread.
RESOLVE: On a strong match (explicit past-reference regex AND FTS5/Chroma top hit above threshold) the assembler injects the matched thread's compacted_summary directly (~200 tokens) and emits thread_recalled; recall_thread remains for weak matches and for fetching the FTS5 snippets. This is the corpus behaviour and costs no LLM call.

### Design §6 'agent owns a small pool: reuse an idle agent session for successive short commands' vs Design §6 'Out of scope here: PTY-backed agent commands' and tools/executor.py:375-392 (one asyncio.create_subprocess_shell per run_command, attach:'sse')
Reuse needs a long-lived shell process; the only long-lived shell today is the PTY session manager, which §6 rules out for agent commands. As written the pool has nothing to pool.
RESOLVE: Either (a) bring a minimal persistent pipe-backed bash with sentinel markers into scope as the pool mechanism (no stdin/sudo, so the PTY seam stays deferred), or (b) drop reuse from this spec and keep one-process-per-command with tidy dock rows. The founder asked for reuse, so (a), stated explicitly with the cwd/env reset rules.

### Design §4 'Recall index: Chroma self_conversations one doc per thread' vs documentation/design/the-being.md §9:224-226 ('retrieval + corpus moving from ChromaDB to SourcePrep — ChromaDB stays for eval only') and explorations.md §10:393 ('No third memory store beyond the G4 ownership split')
The design writes conversation memory to three places: SQLite threads (record), a new production Chroma collection (recall), and Haloysius memories.json (episodic). G4 assigns 'what happened to us' to memory_v2; the design also fixes the HybridMemorySystem vector adapter, which is that store's search path.
RESOLVE: Use SQLite FTS5 over thread summaries as the primary recall index (FEASIBILITY §4 says FTS5 handles 90%) and the repaired Haloysius memory_v2 search for the semantic tier; do not open a new production Chroma collection unless the founder revisits the-being §9.

### Design §1 'thin dividers at thread boundaries (title · relative date)' + §5 ContextBar 'thread' chip + §3 Ctrl/Cmd+N vs founder 'hidden set of sessions under the hood' / 'bolting on parts', memory note ('thread segmentation, compaction and recall are backend mechanisms, not UI navigation'), explorations J1 (dividers are days, 'same being'), CONTINUOUS §3 Layer 1 (temporal dividers '[Monday, Aug 24] [System Boot 08:30]')
A titled divider names the hidden session and makes it a visible object; a keyboard 'new thread' is manual session control; a chip per recalled thread is a list. The corpus's only visible segmentation is temporal, not topical.
RESOLVE: Default to untitled or temporal (day) dividers; keep thread titles server-side only; drop Ctrl/Cmd+N unless the founder asks for manual control; cap the recall chip at one. Put the titled-divider question to the founder rather than shipping it.

### Design §1 'exactly one open thread at a time' + §2 step 6 (new_thread closes the old thread immediately) vs the-being.md §3:102-105 and §4 (decided): the proactive channel opens on its own with a first message that justifies the interruption
A proactive message is a turn from the machine, not the admin. Under the design it has no origin and no thread rule: as a turn it would either become a new thread (closing the admin's open one) or be appended to an unrelated thread.
RESOLVE: Add origin=proactive with the rule 'a proactive turn opens a parallel thread that becomes the open thread only when the admin replies to it'; the dial gates whether it enters the timeline. This is the one place the 'exactly one open' invariant needs an exception.

### Design §5 'HostGreeting as head' vs AgentChat.tsx:656 (HostGreeting is the empty state, rendered only when userMessages.length === 0) and the-being.md §3 (the greeting is the machine introducing itself)
With a persistent timeline the empty state never recurs after day one; rendering the introduction above 50 stored turns turns a greeting into a banner.
RESOLVE: HostGreeting only when the timeline is empty; otherwise the head of a paged load is a day divider (J1) or the newest turns.
