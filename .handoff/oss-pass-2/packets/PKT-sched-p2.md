## 1. Packet

**SCHED-P2** — Honest inactivity-based timeouts + process-group kill.

## 2. User problem

The scheduler's timeout is a flat wall-clock join that lies about what happened. `_call_with_timeout()` in `halbert_core/halbert_core/scheduler/executor.py:62-86` runs the job callable on a daemon thread and does `worker.join(timeout_s)`; when the deadline passes it raises `TimeoutError` while the worker thread keeps executing side effects in the background. The wrapped runner (executor.py:703-756) then records the job as `failed`, writes the receipt as `error` via `self._finish_receipt(receipt_id, 'error', ...)`, and the `exponential_backoff_retry` decorator (executor.py:572, policy from `utils/retry.py`) starts a second run of the same job — so a timed-out-but-still-running first attempt now executes concurrently with its own retry, both mutating whatever the job mutates. This is A06 own-bug 3: the receipt says error while work is still happening, and the retry double-executes it. Second, the timeout is the wrong shape for real workloads: a healthy long job that is actively producing output (a model generation, a large file scan) gets killed at the same flat 600s as a genuinely wedged job that has done nothing. Conversely the streaming LLM path in `halbert_core/halbert_core/model/client.py` (`_stream_chat` at :534, `_chat_once` at :575, `_call_openai_compat` at :668, `_call_ollama` at :757) passes one flat `timeout` to `requests.post`, so a healthy long local generation is aborted at the wall clock, while a mid-generation socket stall sits unnoticed until that same wall clock. Third, when a job's subprocess tree does need to die, nothing kills it as a process group — there is no `utils/process_group.py` yet; the reference pattern (`os.setsid()` at `streaming/pty.py:296`, plus its escalation reaper at :342-445) lives only in the PTY lane. The machine reports a failure while the work continues — exactly the kind of thing that makes it look broken to an operator watching receipts and side effects disagree.

## 3. What to build

Phase 1 (this unit, per the RESHAPE directive): (1) Inactivity-based watchdog replacing the flat wall clock in `_call_with_timeout` (executor.py:62). Give each job run a per-job activity-clock instance using the shared primitive from the `activity_clock` dependency (one `stamp_activity()` / `check_idle()` pair built by extending `agents/turn_activity.py` — `TurnActivity` at :23 already has `stamp()`/`generation()`/`claim()`, so this builds the idle-check half). The job wrapper stamps the clock at run start, after each progress signal the job emits (log line, chunk written, streamed token — stamp at the same points the job already reports progress, not via a model judgment), and a sampler inside `_call_with_timeout` joins in short intervals, comparing `time.monotonic() - last_stamp` against a per-job `idle_timeout` rather than one flat deadline. A job that keeps stamping never trips the watchdog regardless of total elapsed; a job silent for `idle_timeout` is declared idle-dead. `idle_timeout` comes from the job's registration kwargs alongside `timeout_s` (executor.py:408/487 `add_cron_job`/`add_interval_job` signatures gain an optional `idle_timeout_s`, default derived from the existing `timeout_s` so current jobs keep behaving). (2) On idle-death, actually stop the work: route the interrupt through the `process_group` dependency (`utils/process_group.py`, built per backlog §3.1 reusing the pty.py:296 `os.setsid()` + escalation ladder: SIGTERM to the pgid, grace, SIGKILL). Job-subprocess children spawn with `start_new_session=True` and the watchdog kills the process group, so no orphaned grandchildren keep mutating state after the receipt says error. Threads that cannot be killed are at least disowned: the wrapper marks the run interrupted via the activity clock's single-shot `claim()` so the orphaned thread's late completion cannot overwrite the terminal receipt (guard `_finish_receipt` at executor.py:758 and the `update_job_state(... 'completed')` path at :697 against a generation that was already claimed dead). (3) Streaming idle-stall (OC18-M2): in `model/client.py`, change the streaming POST calls (:534, and the stream=True branches at :575/:668/:757) from one flat `timeout` to a `(connect_timeout, read_timeout)` tuple on `requests.post` — `requests` treats tuple element two as the per-read socket timeout, which is exactly an idle-stall bound: each chunk resets it, a mid-generation stall trips it fast, and a long healthy generation with flowing chunks is never aborted. Endpoint selection and the local/cloud pinning are untouched. Also fold in OC14-C18 (hand-teardown of job-owned resources) per the packet note that it only matters when a timeout fires — the idle-death path runs the job's registered cleanup/teardown callback after the process-group kill, before writing the error receipt. Deliver with tests under `halbert_core/tests/` covering: active-long job not killed, idle job killed as a group (no surviving grandchildren), orphaned-thread late completion cannot flip an error receipt to ok, streaming read-timeout trips on stall but not on a long chunked stream.

## 4. What NOT to build

No flat wall-clock replacement deadline that still kills active work — that is the defect being removed, so `timeout_s` becomes an outer bound at most, never the primary trip. No model involvement anywhere in the watchdog: idleness is a measured monotonic-clock comparison, never a judgment call, and nothing here names or routes to an AI model. No change to model endpoint selection, locality pinning, or the `llm_advisory_lock` (priority inversion is SCHED-P4's HM04-C12, not this unit). No new scheduler UI, no dashboard surface, no notifications beyond the existing receipt/log-outcome paths (scheduler status copy stays as-is; golden-text eval is SCHED-P3's dropped HM19-C13). No conversation/thread surface changes — this is scheduler-internal. No turn-liveness watchdog for the agent conversation lock (that is SCHED-P4's HM01-C2, which reuses the same activity-clock primitive but is a separate unit). No cancel-through-live-executor routing, PID+start_time receipt identity, or directory permissions (SCHED-P1's reshape items). No per-job auto-disable streak, ESTOP sentinel, or preflight admission (SCHED-P3). No DaemonThreadPoolExecutor with contextvar propagation and no phase-aware budgets — those are Phase 2 of this packet's own reshape and are excluded below, not silently folded in. No SIGALRM revival: the docstring at executor.py:65-69 already records why signals are wrong on APScheduler's worker pool. No migration or back-compat shim for old receipts; superseded receipt rows stay on disk unread per standing rule.

## 7. Effort

**M** — M is right and this stays inside M because both hard halves already have in-tree anchors. The activity-clock half extends `agents/turn_activity.py` — `TurnActivity` already carries the monotonic stamp, generation counter, and single-shot `claim()`, so the build is the `check_idle()`/sampler half plus wiring stamps into `_call_with_timeout`'s join loop, not a new subsystem. The process-group half is a lift of a proven pattern: `streaming/pty.py:296` (`os.setsid()`) and its escalation reaper (:342-445) are the reference, and backlog §3.1 already names `utils/process_group.py` as the shared module — but the `process_group` dependency is listed for this unit, so that helper may arrive already built; this unit then only consumes it. The streaming idle-stall is genuinely small: changing flat timeouts to `(connect, read)` tuples at four `requests.post` sites in `model/client.py` plus a config surface for the read bound. The real cost is the concurrency correctness in executor.py: the retry decorator (`exponential_backoff_retry`, executor.py:572) must never overlap a live orphaned attempt, the receipt terminal state must be generation-guarded against late thread completion, and the APScheduler worker pool means everything is thread-based. Testing that honestly — fake clocks, real subprocess trees proving group kill, a stalled-socket fixture — is where the M goes. It is not S because three files plus tests plus a shared-primitive integration is more than a day; it is not L because no new architecture, no UI, no cross-process protocol is introduced.

## 8. UX rationale

Nothing user-facing changes shape; what changes is that the machine stops lying. The engaged surface speaks first person grounded in measured data, and receipts are that data: after this unit, when the scheduler says a job failed with "idle for N seconds," that is a measured fact (monotonic clock vs last activity stamp), not a wall-clock guess, and no side effects continue afterward — the process group is dead and the teardown ran. An operator reading the scheduler log or a run receipt sees one of two honest outcomes: `ok` (work completed, nothing was interrupted) or `error: idle timeout` (work was measurably silent for the configured idle bound, process group killed, cleanup done). The distinction an operator can now make — "this long job is healthy and still running" vs "this job is wedged and was stopped" — is the entire UX win: the machine no longer reports failure while work continues, and no job is silently double-run, so effects like a morning brief or a sweep happen exactly once. No new copy, no new colours, no emoji, no notification chrome is introduced; the existing `JobResult.error` string carries the idle-diagnostic message (e.g. naming the phase the job was in when it went quiet, from the last stamp site), which improves later diagnostics without any new surface. The streaming fix is invisible except by absence of pathology: long local generations no longer die mid-answer at an arbitrary clock, so the one seamless conversation stops producing truncated answers that look like the machine broke.

## 9. Acceptance criteria

1) Given a job whose callable sleeps in 1s increments while stamping activity every second for longer than the legacy `timeout_s`, the job completes and its receipt reads `ok` — active work is never killed by elapsed time. 2) Given a job that goes silent (no stamp) for longer than its configured `idle_timeout_s`, the wrapper raises the idle-timeout error, the receipt is finished as `error` exactly once, the job's state is `failed`, and a spawned two-level subprocess tree (child + grandchild, started with new session) has no surviving processes afterward — verified by probing the grandchild's pid. 3) Given the retry policy permits a retry, the retry does not begin while the first attempt's worker thread is still alive, and a late-completing orphaned thread cannot flip the terminal receipt from `error` to `ok` (generation claim blocks it). 4) Streaming: a stubbed HTTP endpoint that sends one chunk then hangs trips the read timeout within the configured bound; an endpoint that streams chunks steadily for longer than the old flat timeout completes without error. 5) The timeout-error message names the last activity stamp site (phase) so the receipt distinguishes "silent during model load" from "silent during execution." 6) No regression in the existing scheduler tests beyond the known main baseline.
