## 1. Packet

**SCHED-P5** — Core lifecycle (bounded shutdown + unclean-exit sentinel + RSS log + thaw reconnect).

## 2. User problem

The Halbert backend process has an unbounded, unobserved lifecycle. (1) `shutdown_event()` in `halbert_core/halbert_core/dashboard/app.py` (lines 1672-1783) runs ten sequential `await ...stop()` calls — `stop_thread_tick_heartbeat(app)` (1678), `stop_mcp_health_monitor()` (1687), `get_terminal_manager().shutdown()` (1720), `_ha_event_stream.stop()` (1729), `_frigate_mqtt_subscriber.stop()` (1739), `_wyoming_agent.stop()` (1749), `audio_coordinator.stop()` (1760), `close_frigate_client()` (1779) — none under a timeout. One hung websocket or MQTT close wedges the whole shutdown and forces the operator to SIGKILL, which is how a graceful stop becomes an unclean death. (2) `run_conversation_boot_hooks()` (app.py:141-172) heals `in_progress` turn rows to `interrupted` on EVERY boot via `tm.mark_interrupted()` (`agents/threads.py:511`) without ever classifying how the last process died or checking the store it is about to trust — a corrupted SQLite store is migrated into before it is inspected. There is no clean-exit sentinel, so "suspicious boot" is not even a computable concept today. (3) The daemon has no periodic RSS measurement: `grep` finds `ru_maxrss`/`memory_info` only in `tools/system_info.py` and `discovery/scanners/process.py` (on-demand probes), never in the daemon's own log — a slow leak is invisible until the machine feels sluggish, which violates "grounded in measured data" because the data is never measured. (4) After a laptop sleep, each integration (`_ha_event_stream` with its flat 5s retry, Frigate MQTT, Wyoming) reconnects on its own private sweep with no coordination; the heartbeat tick (`run_thread_tick_loop`, app.py:795-821) already runs every `heartbeat_s` but never notices that a multi-hour wall-clock gap means the machine thawed, so slots missed while asleep (audit A06-G3) are silently lost and streams stay half-dead until their own retry happens to fire.

## 3. What to build

RESHAPE core, four items, all founder-independent. (1) BOUNDED SHUTDOWN (OC16-C7): in `shutdown_event()` wrap each of the ten awaits in `asyncio.wait_for(..., timeout=SHUTDOWN_STEP_TIMEOUT_S)` (module constant, ~10 s default). Each step records a per-step outcome `closed | uncertain` (TimeoutError or exception → `uncertain`, logged with the step name and elapsed time) and the sequence CONTINUES — a wedged HA-stream stop must not block the terminal-manager shutdown behind it. Emit one summary log line at the end: `shutdown: 9 closed, 1 uncertain (ha_event_stream)`. Also write the sentinel from step (2) BEFORE returning so the next boot can distinguish. (2) UNCLEAN-EXIT SENTINEL (HM11-C2): new module, e.g. `dashboard/shutdown_sentinel.py`. On successful completion of `shutdown_event()`, write a sentinel file (e.g. `<data_dir>/clean_shutdown.json`) recording `{pid, process_start_time, exited_at, steps_uncertain}`; at startup, BEFORE `run_conversation_boot_hooks()` (app.py:1187 call site), read and delete the sentinel. If absent, or pid/start_time does not match what the OS says that pid was (use the shared PID+start_time probe from cross-cutting primitive #2, `utils/process_identity.py` — psutil is already a hard dependency), classify the boot `suspicious` and run `PRAGMA quick_check(1)` (open the store read-only, one connection) against the conversation SQLite store (`agents/threads.py` `SqliteConversationStore`, reached via `get_thread_manager().store`) BEFORE `migrate_legacy_conversations` and `mark_interrupted()` touch it; on `quick_check` failure, log loudly and skip the heal rather than migrating into a corrupt store. Clean boots skip the check entirely. (3) RSS LOG (HM11-C10): a periodic `psutil.Process().memory_info().rss` log line every 300 s — one line, one logger call, no alert logic, no model. Hang it off the existing heartbeat loop (`run_thread_tick_loop`, app.py:795) as a second interval counter, or a tiny separate `asyncio` task parked on `app.state` next to `thread_tick_task` and cancelled in the same bounded `shutdown_event()` step. ~40 lines. (4) THAW RECONNECT (OC16-C8): stamp `time.monotonic()` and `time.time()` on each pass of `run_thread_tick_loop`; when wall-clock delta minus monotonic delta (or the raw wall-clock gap) exceeds a threshold (e.g. > 3× `heartbeat_interval_s()`), the machine slept — call the shared reconnect supervisor (`net/reconnect_supervisor.py`, cross-cutting primitive #6, built once as this packet's named dependency; until it lands, a direct `await` of each integration's existing reconnect entry point is the fallback) to force-reconnect `_ha_event_stream`, `_frigate_mqtt_subscriber`, and `_wyoming_agent` in parallel rather than waiting for their private sweeps. Log one line: `thaw detected after 3.2h; reconnecting 3 integrations`. This also closes A06-G3 (scheduler slots missed while asleep are now visible to the catch-up sweep on the same tick).

## 4. What NOT to build

Per the RESHAPE verdict, do NOT build: sleep/wake suspension lease (OC22-C4 — needs PyObjC in the sidecar plus a generation fence; laptop-only, effort M; deferred, no consumer until founder weighs in); port guardian (OC22-C11 — an orphaned prior backend bumping the next boot's port is a nuisance, not a correctness issue; rated low); event-loop health hysteresis (OC17-C4 — low value, no flapping observed); tri-state readiness (OC17-C5 — low value; `/health` stays as-is); event-loop liveness watchdog (HM11-C1), startup-deadlock watchdog (HM13-C9), restart-loop breaker — all GATED: under no supervisor a hard-exit watchdog converts a wedge into an outage, so these wait on founder decision 2 (macOS lifecycle) and HM11-M2 (exit-code vocabulary + supervisor probe); launchd/LaunchAgent registration — explicitly the SCHED-P5 tail, deferred behind the founder's macOS-lifecycle decision (backlog line 612: macOS-first, not Linux/systemd — do not write a systemd unit either). Also out of scope: any change to `mark_interrupted()`'s heal semantics themselves (the sentinel gates WHEN it runs, not what it does), and any alerting or trend analysis on the RSS series — it is one measured log line, full stop.

## 7. Effort

**S-M** — S-M, matches the registry. (1) Bounded shutdown is mechanical: ten call sites, one `wait_for` wrapper helper, one outcome dict, one summary line — no new state. ~1-2 h. (2) The sentinel is a small new module (~80 lines: write/read/delete/classify) plus a 4-line reorder at the startup call site; the integrity check is a single `PRAGMA quick_check(1)` on a read-only connection, and the pid/start_time probe reuses cross-cutting primitive #2. ~2 h. (3) RSS log is ~40 lines riding a loop that already exists. (4) Thaw reconnect is a monotonic/wall-clock comparison inside `run_thread_tick_loop` (~20 lines) plus a fan-out to three existing reconnect entry points; the hard part (backoff/jitter/stability-window supervisor) is explicitly the named dependency `reconnect_supervisor` (cross-cutting primitive #6, shared with VMV-4's OC10-C9), so this packet consumes it rather than building it — that is why the registry carries the dependency and keeps this packet at S-M instead of M-L. Tests for all four are small and deterministic (fake clock, fake store, fake integration stubs), roughly doubling the code volume.

## 8. UX rationale

Almost nothing surfaces, by design — this is the machine keeping its own house. What an operator notices: shutdown no longer hangs (a hung integration is reported and stepped over instead of forcing SIGKILL); after closing the laptop overnight, Halbert's first-person morning state is grounded — "I was asleep for 7 hours; my home-automation stream and two other connections are re-established" — instead of silently half-dead sensors; the log gains one measured RSS line every 5 minutes so "the machine feels sluggish" becomes a number, not a vibe; and a corrupt state store is caught and announced ("my memory store failed an integrity check; I did not touch it") instead of being silently migrated into. First-person voice in any surfaced message, measured data only, no model anywhere in the packet — the integrity gate and thaw detector are deterministic. No conversation list, no new settings page, no emoji, no colours (the only frontend-visible change is that shutdown and reconnect actually complete).

## 9. Acceptance criteria

(1) Every one of the ten stop awaits in `shutdown_event()` runs under `asyncio.wait_for` with a named per-step timeout; a step that times out or raises is logged as `uncertain` and the remaining steps still execute; the final log line reports the closed/uncertain tally. (2) A sentinel file is written on clean shutdown and consumed at startup; a boot with the sentinel missing or with a pid/start_time mismatch is classified `suspicious` and runs `PRAGMA quick_check(1)` on the conversation store BEFORE `run_conversation_boot_hooks()` heals anything; a failed quick_check skips the heal and logs loudly; a clean boot performs no integrity check. (3) One RSS log line per 300 s appears in the daemon log while idle, sourced from `psutil.Process().memory_info().rss`. (4) A wall-clock jump larger than the threshold inside the tick loop triggers a coordinated reconnect of the HA event stream, Frigate MQTT subscriber, and Wyoming agent (via `net/reconnect_supervisor.py` when landed, direct entry points until then) with a single thaw log line naming the gap and the integration count. (5) None of the deferred tail items (suspension lease, port guardian, event-loop hysteresis, tri-state readiness, any watchdog, launchd) appears in the diff.

## 10. Verification (measured state, not model judgment)

Runnable, measured checks — no model judgment. From the worktree root: `arch -arm64 ./wt_pytest.py halbert_core/tests -k "shutdown_bounded or shutdown_sentinel or rss_log or thaw_reconnect"` against new tests this packet adds (e.g. `halbert_core/tests/test_shutdown_sentinel.py`, `test_app_shutdown_bounded.py`): the bounded-shutdown test stubs one stop() to hang and asserts the full sequence still completes with that step logged `uncertain` (assert on the outcome dict / caplog line, not timing); the sentinel test deletes the sentinel, boots `create_app()`, and asserts `quick_check` ran before `mark_interrupted` (mock-order assertion) and that a `quick_check` failure skips the heal; the RSS test advances a fake clock and asserts one log line per 300 s window; the thaw test injects a wall-clock jump into the tick loop and asserts all three integration reconnect stubs were awaited and the tally line logged. Live measured check: `make dev-restart`, then `curl -s -o /dev/null -w '%{http_code}' http://localhost:8000/health` returns 200 within the shutdown budget (port re-bound after a clean stop — no forced SIGKILL needed); `grep 'rss=' /tmp/halbert-dev*.log | tail -3` shows three spaced lines after 10 idle minutes; and `grep -c 'uncertain' /tmp/halbert-dev*.log` is 0 on a healthy machine while a second run with one integration's port blocked shows exactly 1 and the process still exited 0.
