## 1. Packet

**OTHER-P1** — State backup / recover (merged with plan-MEM-P3 backup scope).

## 2. User problem

Halbert holds all of its own memory locally — state ledger, conversation store, consent ledger, attunement store, audit chain — and has no self-backup of any of it. `discovery/scanners/backup.py` (946 lines) only discovers third-party backup tools; the single tar producer in the tree is `persona/memory_purge.py:294-297`, a bare `tarfile.open(...,'w:gz'); tar.add(source_dir)` with no volatile-path filter, no vanished-file tolerance, and no symlink policy (it follows and archives any symlink planted under a persona memory dir). Two compounding facts make this a live risk, not a hygiene item: (1) a live `.sqlite` plus its `-wal`/`-shm` cannot be tar'd consistently, so even a correct tar archiver produces torn database images — there is no `VACUUM INTO`, `sqlite3_backup`, or `.backup(` call anywhere in the tree; (2) the machine is one disk failure away from total memory loss, which a founder would notice. The ledger also has a correctness leak the backup makes urgent: `continuity/provenance.py` records subjects as `f"file:{path}"` with whatever path spelling the caller passed (un-expanded `~`, relative, symlinked), so the same file accrues parallel triples under different spellings and a backup/verify pass over "what does the ledger assert about this path" answers wrongly. Verdicts: ACCEPT in both FINAL-CRITICAL-DISCOVERY-BACKLOG-2026-09-11.md ("State backup/create-only behavior. Respect no-migration rules") and deep-eval-group4 ("highest-value feature gap in the 'other' bucket"). This unit merges two rows that were duplicates: deep-eval OTHER-P1 (create-only state backup, OC01-C5/C6-snapshot-half/C17) and formal-plan MEM-P3 (`PRAGMA integrity_check` + `halbert backup` with online backup API and verified manifest + `halbert recover` copy-first salvage + durable-write consolidation + provenance subject canonicalisation). Build them as one unit: the archiver is the create path, the snapshot is what makes database entries in the archive self-consistent, recover is the read side that never touches live state.

## 3. What to build

New package surface under `continuity/`, three new modules plus one CLI verb, one provenance fix.

1. `continuity/sqlite_snapshot.py` — `snapshot_sqlite(src: Path, dst: Path) -> SnapshotResult`. Uses `sqlite3.Connection.backup()` (online backup API; takes no write lock on the source), then runs `PRAGMA integrity_check` on the copy plus a page-count sanity check (`PRAGMA page_count` source vs copy). A symlinked source that does not resolve to a regular file fails loudly. Owned-DB discovery is a DECLARED LIST, not a glob: `continuity/state_store.py:180` (`Path(data_dir()) / "state_ledger.db"`), `agents/conversation_sqlite.py:150` (`Path(data_dir()) / "conversations.db"`), `attunement/store.py:85` (`data_subdir("attunement") / "attunement.db"`), the consent store, and the Haloysius home. This discovery list is ALSO the "discover every owned SQLite store" list that DIAG-02's read-only opener needs — build it once here as `owned_sqlite_stores() -> list[Path]` and let DIAG-02 import it (dependency direction: DIAG-02 ships first in M0; this unit lands M3 and reuses DIAG-02's `open_read_only` for the integrity pass where read-only suffices).

2. `continuity/backup.py` — `create_state_backup(state_dir: Path, out_path: Path) -> BackupResult(skipped_volatile, skipped_secrets, entries, retries, stores_snapshotted, manifest_path)`. A `filter=` callback on `TarFile.add` implements: (a) volatile-path rules (`.sock`/`.pid`/`.tmp`, sqlite `-wal`/`-shm` transient companions — normalized with `PurePosixPath` collapsing of `..` before the ancestry check so the filter cannot be bypassed); (b) vanished-file tolerance — a path that raised `FileNotFoundError` on `lstat` and is volatile-matched returns `None` from the filter and is counted in `skipped_volatile`, never fails the archive; (c) symlink containment — `_assert_symlink_contained(entry, root)` runs before every symlink add and refuses any entry whose resolved target leaves the archive root (the `persona/memory_purge.py` hole, closed); no `dereference`, no hardlink dedup — every entry independently restorable. Every `*.sqlite`/`*.db` from the declared owned-store list routes through `snapshot_sqlite` and the COPY goes in the archive, never the live file with its WAL. Retry wraps only EOF/grow-shrink-class `tarfile.ReadError`/`OSError`, 3 attempts, fresh temp path per attempt. Secrets at rest: excluded by a declared deny list reusing the Tier-2 secret paths (`being.yml` peer_token, `.env`, credential stores), excluded count reported in the result — FD-1's recommended default, no `--include-secrets` flag until an encryption decision exists. The manifest (per-entry path + sha256 + size, one JSON document) is written through `utils/durable_write.py` (M0 dependency: temp + flush + fsync + `os.replace` + dir fsync + 0600) so a crash mid-manifest never leaves a truncated one beside a good archive. After writing, the manifest is verified back: re-open the archive, check every manifest entry is present and its digest matches — "verified manifest" is a property of the create path, not a separate command. Snapshot runs AFTER receipt retention prunes (A06-G5, merged R-03) so unbounded receipts don't bloat the archive.

3. `continuity/recover.py` — `recover_state_backup(archive: Path, dest_dir: Path) -> RecoverResult`. Copy-first salvage ONLY, honouring the NO-USERS-YET clause: extracts the archive to a NEW location chosen by the caller, verifies every manifest digest, runs `PRAGMA integrity_check` on every extracted database copy, and reports what is salvageable. It NEVER reads superseded rows into the live store, NEVER overwrites a live database (refuses if `dest_dir` collides with a live store path — compare resolved paths against `owned_sqlite_stores()`), NEVER deletes anything. Restore-into-live is out of scope entirely (founder decision 2 deferred it; that is where the no-migration directive bites).

4. CLI verbs in `Halbert/main.py` following the existing `cmd_*` + subparser pattern (`cmd_audit_verify:364` is the nearest model): `halbert backup` (creates into `state_subdir("backups")` with a timestamped name, prints counts) and `halbert recover <archive> <dest>` (salvage only, prints per-store integrity verdicts).

5. `continuity/provenance.py` — subject canonicalisation: one spelling of the path at the `record_state(f"file:{path}", ...)` call sites (`:233`, `:317`). Add `canonical_subject(path)` (expanduser + `os.path.realpath`, the `file:` prefix applied after) and route both `record_file_change` and `record_file_mode_change` through it, so the ledger holds one triple per real file. Same class of fix as `normalise_mode` (`:116`) which already exists for the mode predicate — one notation per concept. No migration of old rows: superseded spellings stay on disk, unread (standing directive).

## 4. What NOT to build

No restore-into-live: `halbert recover` never writes back over a running store, never imports rows from an old archive into the live ledger — founder decision 2 deferred restore to a separate packet once the archive format has shipped, and the no-migration directive forbids reading superseded data into live state. No encryption of the archive and no `--include-secrets` flag (deferred pending an encryption decision; the default is the declared deny list). No capture-twice-and-diff snapshot variant — the verifier dropped that half of OC01-C6; it exists only to survive a concurrent legacy migration, which Halbert must not have. No off-host/cloud sync, no scheduling of automatic backups (a scheduler job is a separate, later decision — this unit ships the verb). No dashboard button on `Backups.tsx` (explicitly "later" in the deep-eval). No migration or rewriting of existing ledger rows with non-canonical subjects — old spellings stay unread. No changes to `conversation_sqlite.py`'s code (its database is a snapshot SOURCE only — hot-file rule). No `get_subsystem_logger` factory, no redaction work (that is LOG-01+OTHER-P2). No audit-chain checkpoint-and-archive design (that is OC08-C10, a separate design packet aimed at the Haloysius engine). No glob-based database discovery (declared list only — a glob would sweep in foreign databases). No third hard dependency: `tarfile`, `sqlite3`, `hashlib` are stdlib.

## 7. Effort

**M** — M — and this is why the merged unit is one M rather than two separate efforts. The deep-eval scored the create-only backup alone at M ("the tar archiver + SQLite snapshot" with C17 folded in as two test cases) and the formal plan scored MEM-P3 at M; building them separately means two branches both touching `continuity/` and both needing the owned-store discovery list. The work breaks down as: sqlite_snapshot (~M-half — the online-API call is three lines but the integrity verification, symlink-source refusal, and the declared discovery list are the substance); the tar archiver (~M-half — the filter callback, symlink containment, retry classifier, volatile rules against the REAL layout, whose enumeration is the packet's first deliverable per the deep-eval); recover (~S — extract + verify + refuse-live is small once the manifest format exists); provenance canonicalisation (~S — one helper plus two call sites, mirroring the existing `normalise_mode` pattern); CLI verbs (~S — pattern-copy from `cmd_audit_verify`). The L-scored items in the origin (C5 at effort L) shrink because Python's `tarfile` filter callback expresses the volatile/vanish intents more compactly than node-tar's stat-cache synthesis — port the invariants, not the code. Dependencies justify the M3 slot: `utils/durable_write.py` (M0) must exist for the manifest write, and DIAG-02 (M0) ships `open_read_only` plus owns the shared-store-list consumer relationship. Nothing here is gated on a founder decision to START — FD-1 and FD-2 have recommended defaults the deep-eval endorsed (exclude secrets by deny list, create-only + copy-first salvage), so the unit builds to those defaults.

## 8. UX rationale

CLI-only surface; no dashboard in this unit. `halbert backup` prints what the machine did in first person, grounded in measured data: counts of entries, skipped volatile paths, excluded secret-bearing files, snapshotted stores, retries — e.g. "Backed up my state: 4 stores snapshotted and verified, 212 entries, 6 volatile paths skipped, 2 secret-bearing files excluded." It never names an AI model, uses no emoji. `halbert recover <archive> <dest>` prints a per-store integrity verdict ("state_ledger.db: integrity ok, 1,204 rows") and says plainly what it did NOT do: "I copied everything to <dest> and verified it. I have not touched my live state — restoring into it is a separate decision." The refusal case is honest and specific: "that destination is one of my live stores; I will not overwrite it." The first deliverable — enumerating `state_dir()`/`data_dir()` contents (`utils/paths.py:53`,`:63`) — is what makes the volatile filter real rather than ported-from-origin guesses. Secrets exclusion is announced by count, never by enumerating secret paths into a log line. Error text is plain speech as the computer itself: a corrupt archive reports which digest mismatched, not a traceback.

## 9. Acceptance criteria

1. `halbert backup` against a fixture state dir containing a `.pid` file, a `*.tmp` file, a live `state_ledger.db` with open WAL, and a planted symlink to `/etc/passwd`: archive is created; `.pid` and `*.tmp` counted in `skipped_volatile`; the symlink raises and the archive is refused; the ledger database in the archive passes `PRAGMA integrity_check` standalone. 2. Concurrent-write test: rows inserted in one thread while `snapshot_sqlite` runs in another; the copy opens, row count is monotone, `integrity_check == ok`. 3. Manifest verification: corrupt one byte in a produced archive; the verify-back step reports the exact entry whose sha256 mismatched and the backup reports failure. 4. `halbert recover` into a fresh dest: all manifest digests verify, every extracted DB passes integrity_check, live store mtimes and inode unchanged; pointed at a live store path it refuses with nonzero exit. 5. Provenance: two `record_file_change` calls for the same file via different spellings (`~/x` vs `/Users/eric/x` vs a symlinked path) produce ONE current triple in `state_triples` for the canonical subject. 6. Secrets: `being.yml` and `.env` absent from the archive, counted in `skipped_secrets`. 7. A file deleted between listing and add does not fail the archive (vanished-file tolerance). 8. No live store is ever opened writable by recover; no superseded row appears in the live ledger after any operation.
