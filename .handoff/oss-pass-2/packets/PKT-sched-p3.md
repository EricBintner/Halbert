## 2. User problem

Three verified live defects in the scheduler/autonomy layer, plus one standing-rule violation. (1) One broken job halts the entire scheduler: AnomalyDetector keeps a single GLOBAL failure_streak (halbert_core/halbert_core/autonomy/anomaly_detector.py:55,135) even though record_job_outcome(success, job_id) already receives the job id; when the streak crosses config["repeated_failures"] it raises AnomalyDetected, the recovery path calls GuardrailEnforcer.enter_safe_mode() (autonomy/guardrails.py:227), and JobExecutor._wrap_task then skips EVERY job with error='safe_mode_active' (scheduler/executor.py:590). A single wedged cron job safe-modes all autonomous work, and the person is never told in the conversation. (2) The safe-mode/ESTOP flag has two real bugs: guardrails.py resolves Path("data/safe_mode_active.flag") against process CWD (a pause written by a process started in one directory is invisible to one started elsewhere), and is_safe_mode_active() (guardrails.py:272) syncs file->memory only in the True direction, so a flag removed out of band never lifts safe mode. (3) Standing-rule violation: scheduler/autonomous_tasks.py:140-205 asks the MODEL to emit requires_approval in its JSON decision and only ever strengthens a True vote (confidence_threshold dial at :187, high-risk override at :195) — a low-confidence-threshold config lets the model vote its own approval gate down to False. DECISIONS.md is explicit: no LLM makes a permission decision; never a model where a template/deterministic rule suffices. There is no per-job auto-disable, no standing-order document type (zero grep hits), and no first-person announcement when the machine stops doing something on the person's behalf.

## 8. UX rationale

The only user-facing surface is the first-person announcement in the one seamless conversation when the machine auto-disables a job: "I stopped running <job>: it failed N times in a row, most recently with <error>. Say the word and I'll re-enable it." — spoken as the computer itself, grounded in measured receipt data (streak count, last error string), deterministic template, no model judgment, no emoji. Re-enabling is conversational (the person asks; the action is staged and confirmed, never silently executed). Safe mode entered/exited continues to surface via the existing settings route (dashboard/routes/settings.py:2496-2517); the two new states (auto_disabled) appear anywhere job state is already displayed, using shared-token colours only. Standing orders are invisible-unconfigured: with no standing-order file, every autonomous task requires approval exactly as a cautious person would expect; the change removes a hidden model dial (confidence_threshold) rather than adding a visible one. No new panels, no conversation list, no badges.

## 9. Acceptance criteria

1) PER-JOB ISOLATION: with two scheduled jobs A (always failing) and B (always succeeding), after A fails config["repeated_failures"] consecutive times, job A's persisted state is 'auto_disabled' and B still runs to success on its next tick; is_safe_mode_active() remains False throughout (no global safe-mode trip from a routine per-job streak). 2) VISIBLE: the auto-disable produces exactly one first-person announcement message in the conversation store containing the job name, the measured streak length, and the last error string; no announcement is produced for jobs that merely fail below threshold. 3) FAIL CLOSED, MODEL OFF THE GATE: with no standing-order record, _make_decision returns requires_approval=True even when the (mocked) model emits requires_approval:false with confidence 0.99; with a standing order permitting the task class, requires_approval follows the record regardless of model output; the string "requires_approval" no longer appears in the prompt sent to the model. 4) ESTOP: entering safe mode from process P1 (cwd=X) is observed by process P2 (cwd=Y) via the same configured data dir; deleting the flag file out of band causes is_safe_mode_active() to return False on the next call (two-direction sync), and state_machine turn admission plus tools/executor dispatch refuse autonomous work while the flag is present. 5) R-03 NON-DUPLICATION: no new liveness-marker/ticker code exists beyond what R-03's merged tree provides (diff shows zero added lines in the receipt/marker surface).
