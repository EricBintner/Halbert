## 2. User problem

Halbert's founding contract is that it speaks as the computer itself, in first person, grounded in measured data — never assumed. Three concrete places break that contract today, each independently confirmed against the live tree. (1) OC08-C16 / STATE-1: when a sensor is absent, Halbert invents a number instead of saying so. `halbert_core/halbert_core/context/extra_adapters.py:328` (`_get_live_telemetry`) computes `load_avg = os.getloadavg()[0] if hasattr(os, "getloadavg") else 0.0` and then formats `- Load average: 0.00` into the system prompt — on a platform without getloadavg the machine claims a measurement it never took, and 0.00 reads as "idle" which is worse than silence. `halbert_core/halbert_core/dashboard/routes/system.py` has the same unguarded pattern twice: line 54 calls `psutil.getloadavg()` with no all-zero/unavailable check for the vitals JSON, and line 280 calls `os.getloadavg()` bare. No consumer anywhere distinguishes "measured 0.00" from "sensor missing." (2) HM19-C11 / CI-1: Halbert's most expensive recorded footgun is still defended only by a hand-rolled wrapper. The shared venv carries an editable install whose MetaPathFinder pins every `halbert_core` import to the MAIN tree; plain pytest run from a worktree silently tests the wrong code and passes while doing it (memory: halbert-worktree-venv-gotchas). The mitigation is `wt_pytest.py` at repo root — a wrapper every session must remember to invoke, with a documented broken invocation (`arch -arm64 ./wt_pytest.py` under a pyenv shim rejects its own `--asyncio-mode=auto` flag and silently skips every async test, memory: wt-pytest-needs-the-venv-interpreter). The foreign-module set is never asserted; nothing fails the session when a module resolves outside the tree under test. (3) HM13-C17 / CLI-1: `Halbert/main.py:13-15` does `sys.path.insert(0, REPO_ROOT)` but never strips `''`/`'.'` entries and never removes a pre-existing entry whose abspath equals the root — a same-named module in the launch directory (e.g. a stray `halbert_core/` or `config.py` in the user's cwd) shadows the first-party package for the CLI entry point. All three are "assumed, not measured" defects: fabricated telemetry, assumed import resolution, assumed sys.path. Verdict in FINAL-CRITICAL-DISCOVERY-BACKLOG-2026-09-11.md: ACCEPT ("Measured-not-assumed behavior"), effort S, no founder decision gate, hot files named: context/extra_adapters.py, dashboard/routes/system.py, tests/conftest.py, Halbert/main.py.

## 3. What to build

Three independent S-effort items, each shippable on its own, sharing one module and one posture: never report what was not measured. ITEM 1 — `halbert_core/halbert_core/system/vitals.py` (new sibling of the existing `system/display_power.py`): `sample_vitals() -> Vitals` where `Vitals` is a frozen dataclass carrying `cpu_percent: Optional[float]`, `memory_percent: Optional[float]`, `load_average: Optional[tuple[float, float, float]]`, `disk_percent: Optional[float]`, and `unavailable: list[str]`. Rules: every numeric is clamped to finite and to its natural bound (percent to [0,100]); `load_average` is `None` when `os.getloadavg` is missing OR returns an all-zero tuple (all-zero on Unix means the call is a stub, not an idle machine); every omitted sensor is named in `unavailable`. Then migrate the two readers: `context/extra_adapters.py:320-345` (`_get_live_telemetry`) reads `sample_vitals()` once and renders `- Load average: unavailable on this platform` (the string in first person, matching the standing voice) instead of formatting 0.00; `dashboard/routes/system.py:54` routes the vitals JSON through the same sampler so the API emits `load_average: null` plus `unavailable: ["load_average"]` rather than a fabricated 0.0, and line 280's bare `os.getloadavg()` call goes through the sampler too. Do NOT touch `scheduler/autonomous_tasks.py:291`, `federation/telemetry_agent.py:208`, or `tools/system_info.py:125` in this packet — those are internal diagnostics, not user-facing claims; note them as follow-up candidates. ITEM 2 — foreign-module session assertion: a `pytest_sessionstart` hook in `halbert_core/tests/conftest.py` that, after collection-time imports, computes the foreign-module set = every module in `sys.modules` whose `__file__` resolves inside the checkout but outside both the test tree and `site-packages` (the origin tree's term; here: outside `halbert_core/` and the venv), and fails the session with the list if the set is non-empty. Concretely: resolve `os.path.realpath(mod.__file__)`, flag any module whose realpath starts with the main tree's `halbert_core/halbert_core` when the session's rootdir is a worktree (detect by comparing realpaths, not string equality). This replaces the remember-to-invoke part of `wt_pytest.py` for pytest runs — the wrapper stays for its venv re-exec, the assertion makes a wrong-tree import loud instead of silent. Also add `scripts/assert_tree.py`: a standalone CLI (`arch -arm64 .venv/bin/python scripts/assert_tree.py`) that imports `halbert_core`, prints its resolved realpath, and exits 1 if it does not start with the cwd's package dir — usable in CI and ad-hoc session checks without pytest. ITEM 3 — `sys.path` hardening in `Halbert/main.py:8-15`: before the existing `sys.path.insert(0, REPO_ROOT)`, strip `''` and `'.'` entries from `sys.path`, remove any entry whose `os.path.abspath` equals `REPO_ROOT`, then insert. Three lines, comment explaining why (a same-named module in the launch directory must never shadow the first-party package). Keep the existing soft-fail import block untouched. No colours, no emoji, no model names anywhere; the unavailable-sensor string is plain English in first person ("Load average: unavailable on this platform" is the prompt-side rendering; the dashboard JSON stays structural with null + unavailable list).

## 8. UX rationale

The only user-visible change is that Halbert stops claiming measurements it did not take. In the one seamless conversation, when live telemetry is injected into the system prompt on a platform where a sensor is absent, the prompt now carries "Load average: unavailable on this platform" instead of "Load average: 0.00" — the machine says what it knows and what it does not, first person, grounded in measured data, which is the entire premise of how Halbert speaks. On the dashboard, the vitals endpoint (`/api/system/...` served by `dashboard/routes/system.py`) returns `load_average: null` and an `unavailable: ["load_average"]` array when the sensor is missing; the existing VitalsModule frontend already renders absent fields as absent — no new UI, no indicator, no banner, no emoji, no colour change (any rendering of the unavailable state uses shared-tokens and stays understated; if the current frontend cannot render null, the minimal change is to omit the tile's value, not to add a warning style). Nothing is staged, nothing new is executable from the UI. The sys.path hardening and the test-session assertion have no user surface at all — they are integrity guarantees underneath the CLI and the test suite. No AI model is named anywhere: the unavailable string names the sensor, never a provider.
