## 1. Packet

**MCP-C** — Schema cache with lazy connect + idle recycling (post R-09).

## 2. User problem

Every time the Halbert backend boots (or the dashboard health monitor decides a server's config signature changed), `MCPClient.connect()` / `_ensure()` in `halbert_core/halbert_core/mcp/client.py` launches every configured MCP server child process and runs the full handshake + `tools/list` discovery before a single tool is usable — even though the server's tool surface almost never changes between boots. On a single-host macOS steward that means N third-party node/python subprocesses spawned at every dashboard start, each held resident for as long as the dashboard is up, purely to re-answer a question whose answer was already measured last boot. The deep-eval for group 3 (MCP-C section) confirmed this is real but found R-09 (merged on main: ab0750a1 list_changed/diff refresh + breaker-aware probing, d569883d HTTP hygiene + bounded pagination + include/exclude filter, afc2f1b9 tool declaration surface, 58216f33 package preflight) already closed the lifecycle/discovery correctness gaps G11–G16 and G18. What remains is exactly two residuals, both resource optimizations: (a) HM09-C10+M6 — a fingerprint-keyed on-disk schema cache so a boot with a valid cache spawns zero children and connects lazily on first actual tool call; (b) HM09-M11 — idle and max-lifetime recycling of stdio children so a dashboard left open overnight stops holding third-party node processes indefinitely. Today neither exists: grep of `mcp/` shows no schema-cache module and no idle/lifetime reaping — `_Connection` in client.py lives until signature change or death, and `MCPHealthMonitor` in `mcp/health.py` only probes and reconnects, never retires an idle healthy child. The user-visible cost: slower boot of the one seamless conversation surface and idle RAM/process-table pressure on the host Halbert is stewarding.

## 3. What to build

Two narrow pieces, both inside the MCP client/lifecycle surface.

(1) Schema cache with lazy first-call connect. Add `halbert_core/halbert_core/mcp/schema_cache.py`: a small module that reads/writes a JSON cache at `get_config_dir() / "mcp_schema_cache.json"` (same directory `mcp/config.py:config_path()` resolves via `utils.platform.get_config_dir()`), written with 0o600 permissions, atomic write (tmp + rename). The cache is keyed per server by a fingerprint derived from `MCPServerConfig.signature()` (mcp/config.py:370 — the tuple that already includes command/args/env-shape/token-value and must be extended to include `tool_include`/`tool_exclude` from config.py:353-354, since R-09's filter changes the visible tool surface; if signature() does not already cover them, add them to the fingerprint in schema_cache.py rather than changing signature()'s reconnect semantics). Each entry stores: the server's discovered tool schemas (the exact dicts `bridge.py:_list_all_tools`/`list_tools` returns, post-include/exclude filter), a cache-write timestamp, and the fingerprint. Wire it into the discovery path: `MCPClient` gains a lazy mode where, at boot / `connect(server_name=None)` sweep time, a server whose config fingerprint has a fresh cache entry is NOT connected — its cached schemas are handed to `bridge.discover_and_register` (mcp/bridge.py:588) as if discovery ran — and the real connection is established on the first `tools/call` (or any live request) against that server via the existing `_ensure()` path (client.py:1332), which already handles "no connection → connect on demand". On any cache miss, fingerprint mismatch, corrupt JSON, or discovery-versus-cache disagreement detected later (e.g. a `notifications/tools/list_changed` arrives, A17-G11 flag in client.py:405/health.py:392), the behavior fails to eager: connect and re-discover exactly as today, then write the fresh schemas back through the cache after each successful discovery (write-through in `bridge._discover_and_register`'s collect phase or immediately after it returns the count). Cap the cache file size (e.g. refuse entries for servers whose tool list exceeds the bridge's existing per-server tool cap) so a hostile server cannot grow the file.

(2) Idle and max-lifetime recycling of stdio children. In `mcp/health.py`, add optional per-server keys (read from the server's config entry, e.g. `idle_ttl_seconds` and `max_lifetime_seconds`, both default off/absent — opt-in, matching the packet's "optional per-server keys, default off"). The monitor's per-tick sweep (`_check_once`, health.py:318) gains a recycling check: for each live `_Connection` whose transport is a `StdioTransport`, if `now - last_activity > idle_ttl` (track last activity via the existing `note_served_call` hook at health.py:459 plus probe timestamps, or a `last_used_at` stamped on `_Connection` by `MCPClient.request`) or `now - connected_at > max_lifetime`, call `self._client.disconnect(name)` and let the next demand re-`_ensure` it — reaping the child process group via the existing close/`_terminate_group` path (client.py:530). Recycling must respect the reconnect supervisor: an idle-recycled server is a clean disconnect, not a failure, so it must NOT arm backoff (`_arm_backoff`, health.py:496) or increment `reconnect_attempts`; and a server recycled mid-turn is impossible because disconnect only happens when no request is in flight (the client's per-server lock already serializes this).

(3) Adopt the dependency's primitive where it cleanly fits: if `halbert_core/net/reconnect_supervisor.py` has landed (PKT-reconnect_supervisor, M0), `mcp/health.py`'s `_delay_for`/`_arm_backoff`/proven-session reset (health.py:488-501 + `_probe_succeeded`'s A17-G14 rule) should delegate to `ReconnectSupervisor` per-server instances rather than the bespoke math, keeping `ServerHealth.as_dict()`'s public shape unchanged so `/api/mcp/status` consumers don't move. If the supervisor has NOT landed at dispatch time, do NOT block the cache/idle work — keep the existing backoff code untouched and leave the swap as a follow-up note in the commit body.

## 4. What NOT to build

No list_changed/diff-refresh work — R-09 built it (client.py:405 `tools_changed` flag, health.py:392 `_consume_tools_changed`, bridge diff-not-repave). No per-server circuit breaker in the call path — R-09's breaker-consults-health-record is merged; MP-2's shared-breaker question (one primitive across error_recovery.py/tier_router.py/mcp) is explicitly NOT this packet — if a shared breaker primitive is built it goes to MP-2's packet, not here. No proven-session/backoff-reset redesign — A17-G14 stands; this packet must not weaken it (an idle recycle is not a failure and must not touch the budget, but a real failed reconnect still charges it). No HTTP transport changes — redirect pinning, scheme validation, DELETE-on-close, no-session-id-across-cross-origin-redirect are R-09 Phase D, merged (d569883d); the schema cache applies to stdio AND http servers' tool lists equally but must not alter HTTP session handling. No pagination changes — the cursor-set/bytes/deadline bounds in `client.py:_list_paginated` (:1482) stay exactly as-is; cached schemas are written from the already-bounded list walk. No include/exclude filter work — the filter itself (config.py:142-165 `_tool_filter`) is R-09-merged; this packet only feeds its output into the fingerprint. No new dashboard UI, no status-endpoint shape changes (`ServerHealth.as_dict()` keeps its keys; an idle-recycled server simply shows connected:false/health:unknown on next probe), no frontend, no colours/tokens. No migrations: the cache file is new, additive, and deletable at any time — absence means eager connect, exactly today's behavior; old cache files with unknown keys are ignored, never migrated. No reconnect-supervisor build from scratch — that is PKT-reconnect_supervisor's file (`net/reconnect_supervisor.py`); this packet only adopts it if present. No changes to `mcp/server.py` (the server door), `package_preflight.py` (FD-10 fetch-time preflight still runs on every real connect — a lazy first call must still pass `run_package_preflight`, client.py:1179, and a cached schema never bypasses preflight because preflight gates process launch, not discovery). No model involvement anywhere — cache hits/misses and recycling are deterministic; no model ever sees the cache.

## 7. Effort

**S-M** — S-M (one focused session, two files plus tests). The schema cache is the M half: a new ~200-line leaf module (`mcp/schema_cache.py`) with a well-specified key (the existing `MCPServerConfig.signature()` tuple), one read site and one write site in an already-mapped flow (`bridge.discover_and_register` and `MCPClient._ensure`), and a fail-to-eager rule that bounds every mistake to "behaves like today" — the worst a corrupt or stale cache can do is cost one eager connect, because the first real `tools/call` against a lazily-skipped server goes through the unchanged `_ensure()` and any post-connect discovery disagreement is already handled by R-09's list_changed refresh. The idle recycling is the S half: ~60 lines in `mcp/health.py`'s existing per-tick sweep reusing the existing `disconnect()`/`_terminate_group` teardown and the existing `note_served_call` activity hook, default-off per-server config keys so nothing changes for unconfigured operators. Both residuals share the `mcp/health.py` + `mcp/client.py` lifecycle surface, which is why the deep-eval says to build them together. Collision risk is low: lane K serializes MCP-A → MCP-C → TT-02 on `mcp/client.py`, and `mcp/health.py` is otherwise quiet post-R-09. Tests are mechanical: fake config + fake bridge schemas for the cache; monkeypatched `_now()` (the monitor's existing clock seam, health.py:194) for idle/lifetime expiry. What keeps it out of L: no protocol work, no concurrency redesign, no cross-process coordination, and every failure mode degrades to behavior that already exists and is tested.

## 8. UX rationale

No new user-facing surface at all — this is a resource-behavior change the user notices only as absence of friction, which is exactly how a stewarded machine should announce itself. The dashboard boots and the one seamless conversation is ready sooner because the backend no longer spawns N third-party MCP child processes before the first turn; when the user actually calls a tool from a lazily-connected server, the first call takes the connect cost and every later call is unchanged. Nothing renders, nothing is named: log lines say "MCP server '<name>': using cached tool schemas (fingerprint match)" and "'<name>': idle for Ns, closing connection" — server slot labels only, never a model name, no emoji. The status endpoint (`/api/mcp/status`, fed by `ServerHealth.as_dict()`) keeps its existing shape: an idle-recycled server reads as not-currently-connected with no error, which is the honest measured state — the machine reporting "that server is asleep until needed" through the same vocabulary it already uses, first person, grounded in the probe data it actually has. No notification, no pill, no settings page is added in this packet; the per-server `idle_ttl_seconds`/`max_lifetime_seconds` keys live in the existing `mcp_config.yml` the operator already edits, documented in the module docstring. The overnight-idle case is the felt win: a dashboard left open no longer holds third-party node processes resident for days, so the host the user is stewarding has its process table and RAM back — a recoverability/trust improvement on the existing surfaces, not a new one.

## 9. Acceptance criteria

1. Boot-with-cache spawns zero children: with a valid cache file whose fingerprints match the current `mcp_config.yml`, starting `MCPClient` and running `bridge.discover_and_register` registers the cached tools WITHOUT any `StdioTransport.connect()` call (assert via a test spy on `build_transport`/connect: zero launches). 2. Lazy first call: the first `tools/call`-shaped request against a cache-served server triggers exactly one real connect through `_ensure()`, succeeds, and serves the call; subsequent calls reuse the live connection. 3. Fingerprint coverage: editing a server's command/args/env/token AND editing its `tools.include`/`tools.exclude` list each change the fingerprint and each produce a cache miss (eager reconnect) on next boot. 4. Fail-to-eager: a corrupt JSON cache, a cache with an unknown schema version/keys, or a missing file all produce today's behavior (full connect + discovery) with one bounded WARNING log line and no exception escaping `discover_and_register`. 5. Write-through: after any successful live discovery, the cache file exists with 0o600 permissions and contains that server's post-filter tool schemas keyed by the current fingerprint. 6. Idle recycle: with `idle_ttl_seconds: 5` set on a stdio server, driving the monitor's clock past the TTL with no served calls disconnects the server (its child process group is reaped — `transport.alive()` false, process gone) and `reconnect_attempts` stays 0 with `backoff_seconds is None` (no backoff armed). 7. Max-lifetime recycle: with `max_lifetime_seconds` set, a continuously-active server is still disconnected when the lifetime elapses, and the next demand re-connects it. 8. Default off: a server with neither key configured is never recycled regardless of idle time. 9. Preflight still gates: the lazy first connect runs `run_package_preflight` and a preflight refusal surfaces as `MCPDisconnectedError` exactly as an eager connect would (cache never bypasses launch gating). 10. No R-09 regressions: the existing MCP test files (test_mcp_client.py, test_mcp_health.py, test_mcp_bridge.py, test_mcp_transport_hygiene.py, test_mcp_http_and_pagination.py) pass unchanged apart from the known-red baseline.
