## 1. Packet

**process_group** — Process-group start/kill escalation.

## 2. User problem

Halbert has three separate code paths that spawn child processes and need to kill them on timeout or shutdown, and they each handle process-group ownership and kill escalation differently — one does it right, one does it half-right, one does it wrong. The shell executor fallback path (`halbert_core/halbert_core/tools/executor.py:940-1017`, `_run_command`) spawns with `asyncio.create_subprocess_shell` and NO `start_new_session=True`, and its timeout handler does `proc.kill(); await proc.wait()` — a bare SIGKILL to the `/bin/sh -c` wrapper only. Every grandchild the shell spawned (a `make` that launched compilers, a script that called `npm`, a pipeline stage) is orphaned and keeps running after the tool call returns, holding the conversation's output buffers and any resources it grabbed. The scheduler's bounded-execution helper (`halbert_core/halbert_core/scheduler/executor.py:62-86`, `_call_with_timeout`) is a thread-join bound that leaves the timed-out worker thread running with live side effects — when SCHED-P2's inactivity watchdog lands it will need to kill the worker's subprocess as a group, and today there is no shared helper to do that. The MCP client already solved this correctly in R-09 (`halbert_core/halbert_core/mcp/client.py:447` `start_new_session=True`, `:530-569` `_terminate_group`: SIGTERM the pgid, grace, SIGKILL, reap), and the PTY session does its own variant (`halbert_core/halbert_core/streaming/pty.py:296` `os.setsid()`, `:434-474` `_escalate_kill`). The standing rule forbids a third (fourth) duplicate primitive: the terminal-tools and scheduler residuals must reuse one escalation ladder, not invent new ones. The defect is confirmed live by the deep-eval: "executor.py spawns with no start_new_session and the timeout path is an immediate SIGKILL to /bin/sh only, so every shell timeout orphans grandchildren."

## 3. What to build

A new module `halbert_core/halbert_core/utils/process_group.py` exporting one small sync/async pair of helpers that own the whole spawn-to-reap escalation ladder, extracted from the R-09 MCP implementation (the reference) and generalised. Concrete contents: (1) `GROUP_TERM_GRACE_SECONDS = 3.0` and `GROUP_KILL_REAP_ATTEMPTS` / `GROUP_KILL_REAP_INTERVAL_S = 0.05` constants, values taken from the MCP `_terminate_group` ladder and the PTY `_escalate_kill` reaper. (2) `spawn_kwargs() -> dict` returning `{"start_new_session": True}` — the one keyword every `asyncio.create_subprocess_shell` / `create_subprocess_exec` call site must pass; a named helper rather than a bare literal so the grep-able choke point exists and a future platform note has one home. (3) `get_group_id(pid: int) -> Optional[int]` wrapping `os.getpgid` with the try/except that returns `None` on a race (already the pattern at `mcp/client.py:464-467`). (4) `async def terminate_group(proc, pgid, *, term_grace: float = GROUP_TERM_GRACE_SECONDS, log=None) -> None` — the exact ladder lifted from `mcp/client.py:530-569`: if `pgid is None` fall back to `proc.kill(); await proc.wait()`; else `os.killpg(pgid, SIGTERM)` treating `ProcessLookupError` as "clean exit, nothing left" (not an error), wait up to `term_grace` for `proc.wait()` (or `asyncio.sleep(term_grace)` if the direct child already exited, since a launcher returning is not the group exiting), then `os.killpg(pgid, SIGKILL)`, then a bounded WNOHANG reap retry so a signal delivered asynchronously does not leave a zombie (the R04-F12 fix the PTY reaper encodes at `streaming/pty.py:464-474`). `PermissionError`/`OSError` on the killpg is logged at debug and swallowed, matching the MCP original — signalling is best-effort cleanup, never a crash vector. (5) A module docstring stating the accepted residual risk verbatim from the MCP docstring: a pgid can in principle be reused between spawn and terminate; Halbert is a single-host steward with a handful of children, and leaving a process running with closed pipes is the worse of the two outcomes — so the risk is accepted and documented, not fixed. Wiring in this unit is limited to the module itself plus converting the two known-live call sites: `tools/executor.py:940` gains `start_new_session=True` via `spawn_kwargs()`, its timeout path at `:1011-1017` replaces `proc.kill()` with `await terminate_group(proc, pgid)`, and it captures `pgid = get_group_id(proc.pid)` right after spawn; `mcp/client.py:_terminate_group` is re-pointed to delegate to the shared helper (delete the private copy, keep the public behaviour). `streaming/pty.py` keeps its own `_escalate_kill` — it manages a raw `os.fork()` child, not an `asyncio.subprocess.Process`, so it does not fit the helper's `proc` signature; the module docstring names it as the fork-side sibling and says the ladder semantics are deliberately identical. The scheduler adoption is NOT wired here (SCHED-P2's watchdog does not exist yet); the helper is built so SCHED-P2 consumes it without changes. Tests: a new `halbert_core/tests/test_process_group.py` (see verification). No standing-rule surface is touched: no UI, no model, no colour, no emoji, and the helper is a deterministic OS call — never a model where a template suffices.

## 4. What NOT to build

Do not migrate `streaming/pty.py` onto the helper — its child is a raw `os.fork()`, not an `asyncio.subprocess.Process`; its `_escalate_kill` already works and reworking it risks the terminal surface for zero gain. Do not build the SCHED-P2 inactivity watchdog itself, the phase-aware budgets, or the DaemonThreadPoolExecutor — those are SCHED-P2 Phase 1/2 items; this unit only ships the shared kill primitive they will call. Do not touch `scheduler/executor.py:_call_with_timeout` (the thread-join bound and the `status='timeout'` receipt fix) — that is OTHER-P4's `utils/deadline.py`, a different packet; process_group and deadline are siblings, not the same module. Do not add a PID+start_time identity fingerprint to the helper — that is TT-01/SCHED-P1's separate shared item (OC06-C13); killpg pgid-reuse risk is documented and accepted, not fingerprinted, per the MCP docstring. Do not build a process registry, background task tracking, or `poll/log/wait/write` surface — that is TT-04's ProcessRegistry. Do not change `tools/executor.py`'s pool path (`streaming/agent_pool.py`) — the pool runs through PTY sessions which already setsid; only the subprocess fallback is in scope. Do not add Windows support — the whole tree is Unix-only (`os.fork`, `os.killpg`), macOS + Linux for v1, matching `streaming/pty.py:13`. Do not add a synchronous flavour of the ladder for general use; the only sync caller is the PTY fork path which keeps its own. No new dependencies — `os`, `signal`, `asyncio`, `logging` only, respecting the two-hard-dependency contract.

## 8. UX rationale

No user-facing surface — this is an internal OS-correctness primitive. The user-visible effect is indirect and behavioural, felt through the surfaces Halbert already owns. Before: the founder stages a command in the one seamless conversation, the agent runs `make` in a shell block, the command hits its timeout, the tile shows a red exit marker — and the compilers the make spawned keep running invisibly, fan spinning, load average climbing, the next turn's vitals reading showing a machine under load for no stated reason. That contradicts the first-person grounded-in-measured-data stance: the machine would be reporting load it caused and cannot account for. After: a timed-out shell block kills the whole process group, the terminal tile's exit marker is the truth (the process tree is actually gone), and the load the machine reports is load it did not secretly cause. There is no notification, no pill, no copy change — the watched terminal simply stops lying about whether the command is over. This upholds the "commands staged from the UI are staged, never executed" and "watched terminals" directives: when a staged command is bounded, the bound is real, not a SIGKILL to a wrapper that orphans the work.
