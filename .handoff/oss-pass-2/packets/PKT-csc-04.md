## 1. Packet

**CSC-04** — Session-tree integrity (corruption quarantine).

## 2. User problem

The conversation store — the one seamless conversation, with no backups — still writes into a damaged file under a confirmed classifier bug, and opens three independent connections on the same database file. Specifically: (1) `_is_fts_write_corruption_error` at `halbert_core/halbert_core/agents/conversation_sqlite.py:1185-1211` returns True for a bare `'malformed' in msg` (line 1206: `if "corrupt structure" in msg or "malformed" in msg: return True`), so a whole-file structural error like `database disk image is malformed` with no FTS attribution routes into `_enter_fts_fail_open` — whose contract is "the canonical write continues." That is the exact compounding Hermes documents (a handle kept writing ~50 minutes and turned a readable file unopenable on shutdown). The function's own docstring admits "a bare malformed image is structural" and then routes it to fail-open anyway. (2) Three sites mint independent `SqliteConversationStore` connections on the same resolved path — `agents/threads.py:1297,1306` (`_create_conversation_store` fallback paths), `dashboard/routes/guest.py:640`, `dashboard/routes/conversations.py:73` (module-level singleton) — each with its own lock and a bare `conn.close()` (`close()` at :3868); one connection's close-time checkpoint can race another's growth (lost/reordered page-write corruption). (3) `cur.execute("PRAGMA journal_mode=WAL")` at :786 discards the returned row — there is no verification the file actually entered WAL, and no predicate gating new-file WAL despite `sqlite_wal_reset_vulnerable()` (:63) already existing and only logging. (4) No startup integrity detection: no `PRAGMA quick_check`/`integrity_check` anywhere; a store that passes the 16-byte header preflight (`_file_is_unreadable_db`, :642) but has a damaged B-tree is discovered only when a write dies mid-turn. (5) No error taxonomy: `SQLITE_BUSY` (transient), `SQLITE_CORRUPT`/`SQLITE_NOTADB` (sticky-quarantine), and `SQLITE_FULL`/`SQLITE_IOERR` (environmental) all collapse into the same WARNING-and-return-None path, so a busy retry and a damaged file are indistinguishable to callers. (6) No freelist-gated maintenance: nothing ever vacuums or checkpoints the conversation store; `journal_size_limit` is unset (A08-G11). (7) No progress-handler deadline on store reads, so a contended lock or slow page-in can park a turn indefinitely. R-04 (merged) covered fsync pragmas, FTS fail-open, column reconciliation, the one-open-leaf index, A08-G1/G2/G7/G8/G12 — but deliberately not the classifier split, the registry, the taxonomy, startup integrity, or maintenance. Founder decision 1 (gate new-file WAL on the version predicate, never downgrade, log at startup) and founder decision 9 (startup integrity posture) govern items 3 and 4.

## 3. What to build

All work in `halbert_core/halbert_core/agents/conversation_sqlite.py` unless noted; tests in `halbert_core/tests/test_conversation_store_corruption.py` (extend — 28 tests already there) plus a new `halbert_core/tests/test_conversation_store_registry.py`.

1. **Classifier split (the defect fix).** Rewrite `_is_fts_write_corruption_error` (:1185) so a bare `malformed` / `not a database` / `SQLITE_NOTADB` message with no FTS attribution (`fts5:` prefix or `messages_fts` mention) is NOT fail-open. Add a module-level `class StoreCorruptError(RuntimeError)` beside `RedactionFailed` (:571). At the three `_enter_fts_fail_open` call sites (:1630, :1714, :2527, :2691) and in `append_message`/`append_receipt`, route a bare-structural error to: set `self._structurally_corrupt = True` (the sticky flag R-04 added, :695/:973), raise `StoreCorruptError` naming the db path, and skip the close-time checkpoint (best-effort `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` via `setconfig` where available, guarded) so the -wal survives for forensics. Keep `SQLITE_CORRUPT_VTAB` and `messages_fts`-attributed messages on the existing fail-open path — a corrupt index still degrades to LIKE, never bricks the store. Writes after the sticky flag is set fail immediately at the `_structurally_corrupt` check; no reopen clears it in-process.

2. **Error taxonomy.** Add `classify_sqlite_error(exc) -> str` (module function) returning one of `"busy"`, `"damaged"`, `"disk_full"`, `"io"`, `"interrupted"`, `"other"`, checked in that order — `damaged` (SQLITE_CORRUPT/NOTADB codes and bare-malformed messages) BEFORE `disk_full`/`io`, because a corrupt file can surface as an I/O error. Use `sqlite_errorcode` when present (dead on this venv's Python 3.10.9 — keep the message arm primary, as `is_structural_corruption` already documents at :592-594). Wire it into the WARNING lines in `append_message` and the health-route surface so `_last_init_error` (:688) carries the class, not just the string.

3. **Refcounted shared-store registry.** Module-level `acquire_store(path: Optional[str] = None) -> SqliteConversationStore` and `release_store(store) -> None` in `conversation_sqlite.py`: one store per resolved absolute path, refcounted; `close()` on a shared instance decrements rather than tears down; actual `conn.close()` runs outside the registry lock. Route the three construction sites through it: `threads.py:1297,1306`, `dashboard/routes/guest.py:640`, `dashboard/routes/conversations.py:73`. Skip generation/retirement (no snapshot-restore re-points the inode) — this is the small version the deep-eval scoped; the multi-process precondition is unproven since the scheduler runs in the dashboard process.

4. **WAL pragma row reading + new-file gate (founder decision 1).** At :786, read the row `PRAGMA journal_mode=WAL` returns; if the mode did not become `wal`, log it once with the actual mode. Gate: only issue the pragma at all when the file is new (did not exist before this open) AND `sqlite_wal_reset_vulnerable()` is False — never issue a downgrade pragma against an existing WAL file. Keep the existing `warn_if_wal_vulnerable()` startup log as-is.

5. **Zeroed/unreadable preflight — already merged; extend to the startup integrity check (founder decision 9).** `_file_is_unreadable_db` + `quarantine_unreadable_db` already handle the header cases. Add a throttled `PRAGMA quick_check` run at first `acquire_store` per boot (after schema open, before serving): on failure, set `_structurally_corrupt`, quarantine via the existing `quarantine_unreadable_db` (move-aside, never delete), record `_last_init_error` with the `damaged` class, and surface a first-person line through the health route ("I found damage in my conversation store and moved it aside; nothing was deleted"). Full `PRAGMA integrity_check` stays on-demand (feeds MEM-P4's doctor later — expose the runner as a module function `run_integrity_check(path)` so DIAG-02 can reuse it).

6. **Freelist-gated startup maintenance.** In the same first-acquire hook (after the quick_check), compute `freelist_count / page_count` via pragma reads; only when ratio exceeds a threshold (0.25) AND an interval has elapsed (stamp in `store_meta`, which R-04 created at :1077) AND a module-level maintenance lock is free (skip-not-block, never wait), run `PRAGMA wal_checkpoint(TRUNCATE)` then `VACUUM`. Set `PRAGMA journal_size_limit` (A08-G11) at open alongside the Darwin durability pragmas (:793-798). Never raises — maintenance failure is a log line.

7. **Progress-handler deadline on reads.** `set_progress_handler` on the connection with an instruction-count budget on the search/read paths, aborting (SQLITE_INTERRUPT → taxonomy `"interrupted"`) past the budget so a contended or slowly-paged read cannot park a turn; cleared on write paths. Keep it small — one helper `_install_read_deadline(seconds)`.

8. **End-reason taxonomy (small rider).** Where turn/store closes record outcomes, classify close/abort reasons with the same `classify_sqlite_error` vocabulary so the health surface can say why the store last stopped, in measured terms.

Halbert frame: every user-facing string (health route, startup line) is first-person as the computer, names no AI model, uses no emoji. Quarantine is always move-aside, never delete (standing directive). No migrations — all additions are new tables in the existing `store_meta`/new module functions.

## 8. UX rationale

Almost entirely invisible by design — this is integrity plumbing under the one seamless conversation. The only surfaces: (1) the health route, which already exposes `_last_init_error` and now also carries the error class (`damaged`/`busy`/`disk_full`) and the quarantine path when one happened; (2) a single first-person line at startup when quick_check fails or a file was quarantined: "I found damage in my conversation store and moved it aside to `<path>`; nothing was deleted." — spoken as the computer, grounded in the measured pragma result, naming no model, no emoji, colours only from shared-tokens if rendered in the dashboard; (3) log lines: exactly one `fts_fail_open`-style single WARNING per degradation event (the existing pattern at :1233), one startup INFO for the WAL posture (already present), one ERROR per quarantine (already present at :631). Nothing else changes for the founder: no conversation list appears, no settings toggle is added (WAL posture is founder decision 1, a ruling not a preference), commands remain staged never executed, and a store under maintenance simply skips its vacuum when the lock is held — no spinners, no blocking, no notification for the routine path. A damaged store fails closed (writes raise `StoreCorruptError`) rather than silently degrading — the user-visible effect is an honest "I can't write to my store right now" instead of the current silent loss.

## 9. Acceptance criteria

1. A bare `database disk image is malformed` (no FTS attribution) raised during `append_message` sets `_structurally_corrupt`, raises `StoreCorruptError`, and no further write reaches the file — while a corrupt `messages_fts` (`fts5: ... corrupt structure` or `no such table: messages_fts`) still enters fail-open and search falls back to LIKE. 2. `acquire_store(path)` called twice with the same resolved path returns the same connection object; `release_store` decrements; the last release closes the connection; `threads.py`, `guest.py`, and `conversations.py` no longer construct `SqliteConversationStore` directly for the default path. 3. On a new file with a non-vulnerable SQLite build, `PRAGMA journal_mode` reads back `wal`; on a WAL-reset-vulnerable build the pragma is not issued for a new file and the log says why; an existing WAL file is never issued a downgrade. 4. A store whose B-tree fails `PRAGMA quick_check` at boot is moved aside via `quarantine_unreadable_db` (file exists at `<db>.corrupt-<timestamp>`, original replaced by a fresh store), `_last_init_error` names the `damaged` class, and the health route exposes it. 5. `classify_sqlite_error` orders damaged before disk/io: a `SQLITE_CORRUPT` and a `SQLITE_FULL` input classify distinctly. 6. A store under the freelist ratio is not vacuumed; a concurrent holder of the maintenance lock causes a skip, not a wait. 7. A read that exceeds the progress-handler budget aborts with the `interrupted` class instead of parking. 8. All pre-existing corruption tests (the 28 in `test_conversation_store_corruption.py`) still pass unchanged — fail-open contract, quarantine-never-delete, `HALBERT_DATA_DIR` refusal, and schema-version refusal are untouched.
