## 2. User problem

Halbert's diagnostic surface speaks two incompatible shapes. `utils/health.py` emits its own `HealthCheck` dataclass (name / status healthy-degraded-unhealthy / message / details dict), while `findings/store.py` already defines the canonical `Finding` shape (severity, the Four Whys with `why_trust` path:line provenance, affected_paths, fix linkage via proposal_id) persisted in SQLite and surfaced through the findings API and dashboard bell. Every new health or diagnostic check must pick a side, and anything that picks `HealthCheck` is invisible to the findings pipeline — no severity routing, no provenance, no snooze/dismiss lifecycle, no proactive event. Two further gaps sit on top of that split. First, `mcp/client.py:428-455` (`MCPStdioClient.connect`) launches whatever executable `MCPServerConfig.command` names — a string read from `mcp_config.yml` (`mcp/config.py:229-235`, `config_path()`), which is user-writable; audit gap A17-G3 confirmed a `write_file` to that file classifies MEDIUM on macOS and the health monitor reconnects within one tick, so a planted config silently swaps the binary the host's steward spawns. There is no content-hash verification of the resolved binary against what was approved at setup. Second, redaction coverage is tribal knowledge: `security/display_transport.py` enforces the registry choke point for the `tool_start`/`tool_complete` seam, but no artifact enumerates which egress seams (MCP response path, dashboard websocket, TTS/voice path, terminal stream, scheduler receipts) are captured, proxy-only, or uncovered — a gap only discoverable by reading every seam's source. Underlying all three: the OSS pass-2 T5 packet was scoped assuming R-15's eval harness was merged on main; it is not. Verified against git: `fix/remediation-sonnet-batch-1` still carries 20+ commits not on main (`git log fix/remediation-sonnet-batch-1 --not main`), and its diff touches `continuity/eval_consolidation.py`, `continuity/recall_eval.py`, and their tests. So the genuine residual on this unit is the three R-15-independent items: findings-shape unification, SHA-256 artifact verification, and the coverage registry.

## 3. What to build

Three deliverables, all under or adjacent to the findings/health surface. (1) Findings-shape unification: route `utils/health.py`'s check results through `findings/store.py`'s `Finding` shape instead of the parallel `HealthCheck` dataclass. Concretely: add a thin adapter — one function in `utils/health.py` (or a new `findings/health_bridge.py`) that converts each check's outcome into a `Finding(detector="health", severity=..., why_now=..., why_care=..., why_so=..., why_trust=["<check fn path:line>"])` and hands it to `FindingStore.add()` (findings/store.py:196). Keep the existing `HealthCheck` dataclass as the checks' local return type (callers like `get_system_health()` at health.py:235 and the dashboard readiness probes consume it); the change is that every check ALSO emits a Finding into the store — one write path, one severity vocabulary, free snooze/dismiss/bell integration. Do not grow a second parallel persistence shape. (2) SHA-256 artifact verification for MCP stdio servers: a new module, e.g. `mcp/artifact_pin.py`, exposing `verify_server_binary(config: MCPServerConfig) -> Optional[Finding]`. It resolves `config.command` (which may be a bare name on PATH or a path), rejects any resolution that traverses a symlink whose ultimate target differs from the pinned target, hashes the resolved binary with hashlib.sha256, and compares against a manifest stored next to the config (e.g. `get_config_dir()/mcp_artifact_pins.json`) whose entries are written at first approval of each server (the moment the config write path at mcp/config.py:805+ accepts the server). On mismatch, missing pin, or symlink rejection it returns a critical-severity Finding and the connection path in `MCPStdioClient.connect` (mcp/client.py:428) refuses to spawn — fail closed, matching the display_transport fail-closed precedent (A05-G11). Wire the check as a registered health/finding detector so it also runs on the monitor tick, since the monitor is what reconnects after a config edit. (3) Coverage registry: a static, in-repo table — one module, e.g. `security/redaction_coverage.py`, carrying a list of named egress seams (MCP response choke point at `security/display_transport.py`, dashboard websocket turn-event tee, TTS/voice output path, terminal stream, scheduler receipts) each annotated `captured` / `proxy-only` / `uncovered` with a one-line evidence pointer (path:line of the enforcing call, or of the seam lacking one). Expose it as a detector that emits one warning Finding per `uncovered` seam, so the documentation is load-bearing: a new seam added without a redaction path shows up in the findings store instead of in a doc nobody re-reads. This registry consumes the redaction registry's output; it documents where enforcement exists, it does not re-implement enforcement.

## 8. UX rationale

Nothing in this unit adds a user-facing surface; it changes what the surfaces that already exist can say. After unification, health-degraded states appear in the one place the founder already looks — the findings feed behind the dashboard bell — with the same severity vocabulary, `path:line` provenance in `why_trust`, and snooze/dismiss controls every other finding has, instead of living only in a doctor printout. That matters for the steward frame: the system speaks as the computer itself, first person, grounded in measured data — a Finding emitted by `check_memory()` IS measured data entering the seamless conversation's recall path, where a `HealthCheck` tuple was not. The artifact verification's user-visible behavior is a refusal: when a pinned MCP server binary's hash changes (or its path re-resolves through a new symlink), the server does not launch and a critical Finding explains, in the findings feed, which server, which path, and that the content no longer matches what was approved — staged, never executed; the founder re-approves by re-pinning, never by the system auto-healing. The coverage registry's only direct UX is that uncovered redaction seams show up as standing warning findings rather than as surprises in a future audit. All copy must follow standing rules: no emoji anywhere, no AI model named on any surface (findings name servers, paths, and hashes, never providers/models), colors only from shared-tokens if any dashboard text is touched.
