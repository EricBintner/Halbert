## 1. Packet

## 2. User problem

The Halbert dashboard frontend keeps the host busy answering polls nobody reads and has no single owner for two cross-cutting behaviours. First, polling is ad hoc: 29 `setInterval` call sites are scattered across `halbert_core/halbert_core/dashboard/frontend/src` (verified count) — pages/Dashboard.tsx:61 (metrics, 2 s), pages/Approvals.tsx:36, pages/GPU.tsx:171, pages/Containers.tsx:159, components/Layout.tsx:244 and :482 (5 s approvals + 2 s status), components/modules/VitalsModule.tsx:56, components/fleet/NodeFleetCockpit.tsx:104, hooks/useDiscoveredPeers.ts:74, hooks/useHostIdentity.ts:118, and ~19 more. Each hand-rolls its own interval with no shared notion of TTL, no pause when the Tauri window is hidden (a window left open all day polls at full rate), no interruption when a manual refresh lands, and no coalescing when two components want the same endpoint. Second, reconnects are hand-rolled per socket: hooks/useDashboardTurnReflection.ts:35 pins a fixed `RECONNECT_MS = 5_000` on the `/ws` WebSocket and ignores the close code, and hooks/useBeingEvents.ts:195-196 pins a fixed 3 s on the `/api/being/events` EventSource; the backend already closes an unauthenticated WS handshake with code 1008 "unauthenticated" (dashboard/auth.py:478-479), but neither client stops on it — an expired token means a permanent 3–5 s reconnect hammer against a 401. Third, there is no skill disable surface: `skills/readiness.py:133` (`disabled_skill_names()`, backed by `skills_config.yml` under `utils.paths.data_dir()`, keys `disabled` and `disabled_by_platform`) is the operator's only off switch, and it is edited by hand in YAML; the deep-eval (HM10-C20 + A13-G10) confirms no settings UI lists skills, their readiness state, or lets the operator turn one off. The user-visible cost: idle CPU and fan on the host the machine stewards, a reconnect storm that looks like a hung app after token rotation, and an operator who must hand-edit YAML to silence a misbehaving skill.

## 3. What to build

Three pieces, all frontend-owned, landing on the packet's two target files plus their tests. (1) `hooks/usePolling.ts` [new file] — a typed refresh-policy hook: `usePolling(fetcher, { ttlMs, enabled?, refreshOnFocus?, key? })` that (a) pauses when `document.visibilityState === 'hidden'` and resumes with an immediate refresh on `visible`, (b) treats `ttlMs` as a stale-after, not a metronome — re-entry with fresh data is a no-op, (c) exposes an imperative `refresh()` that interrupts and supersedes the pending timer (a manual pull resets the clock), and (d) coalesces concurrent in-flight calls to the same `key` so two mounts of the same policy share one request. Migrate a representative, bounded set of the dumbest fixed-interval sites to it — pages/Dashboard.tsx:61, pages/Approvals.tsx:36, pages/GPU.tsx:171, pages/Containers.tsx:159, components/Layout.tsx:244/:482, components/modules/VitalsModule.tsx:56, hooks/useDiscoveredPeers.ts:74 — leaving tick-style clocks (TerminalTile's 1 s `setNow`, StandbyController's clock, animation timers) on raw setInterval since they are render-time, not fetch-time. Export it from hooks/index.ts. (2) `pages/SkillsSettings.tsx` — a settings-owned skills page following the existing settings-tabs pattern (lazy import in pages/Settings.tsx:64-75 style, registered as a tab beside Knowledge/Safety; the packet target path is `pages/`, so the page component lives there and renders as the tab body). It lists skills from the registry (name, description, readiness state per `skills/readiness.py` Readiness enum READY/MISSING/UNSUPPORTED/DISABLED) with a per-skill toggle writing the `disabled` list in `skills_config.yml`; a disabled skill is omitted from matching. Because no `/api/skills` route exists today (verified: no skills router under dashboard/routes/), this unit adds the thinnest read/write endpoints it needs (GET list + PUT disabled list) as part of the page's plumbing — keep them in the settings route family, not a new subsystem. Text names skills by their SKILL.md name, never any model. Colours strictly from shared-tokens; no emoji. (3) Reconnect owner — a small TS policy helper (colocated in usePolling.ts or a sibling `hooks/reconnectPolicy.ts`, frontend-mirroring the `reconnect_supervisor` dependency's contract: floor 3 s for localhost, doubling to a ~60 s cap, reset on successful open, stop-and-surface on close code 1008) and wire both call sites to it: useDashboardTurnReflection.ts:83 and useBeingEvents.ts:195-196. On 1008 both hooks stop retrying and surface a visible "reauthenticate" state instead of looping; any other close code follows the bounded backoff.

## 8. UX rationale

This is hygiene the operator feels as the machine being a better resident of itself, in Halbert's first-person voice. The typed refresh policy means a Tauri window left open all day stops polling at full rate while hidden — the computer stops asking itself questions nobody is reading, and resumes current the instant the window is focused again (an immediate refresh on `visible`, not a stale catch-up). That is the "grounded in measured data" directive applied to the dashboard's own metabolism: numbers on screen are fresh because something looked, not because a timer fired. The skills settings page gives the operator a visible, reversible off switch where today there is a hand-edited YAML file: each skill appears by its SKILL.md name with its readiness state (ready / missing / unsupported / disabled), and disabling one is a toggle, not a text editor. The page is settings-owned and quiet — a tab beside Knowledge and Safety, not a new nav destination — consistent with the founder's ruling that settings own configuration surfaces. The reconnect owner removes a failure mode the operator currently reads as a hung app: after token rotation the being-events feed and turn reflection stop silently hammering a 401 every 3–5 s and instead show a plain reauthenticate state. All copy speaks as the computer in first person ("I can't reach my skills config" not "the server returned 401"), names the slot never the model, uses shared-token colours only, and carries no emoji.

## 9. Acceptance criteria

1) `hooks/usePolling.ts` exists and is exported from `hooks/index.ts`; the migrated fetch sites (Dashboard, Approvals, GPU, Containers, Layout approvals/status, VitalsModule, useDiscoveredPeers) no longer contain a raw `setInterval` for those polls — `grep -rn "setInterval" src/pages/Dashboard.tsx src/pages/Approvals.tsx src/pages/GPU.tsx src/pages/Containers.tsx src/components/Layout.tsx src/components/modules/VitalsModule.tsx src/hooks/useDiscoveredPeers.ts` returns zero fetch-poll hits (render-tick timers elsewhere may remain). 2) Polling pauses hidden: with the document hidden, no fetch fires for a migrated policy; on return to visible, exactly one refresh fires immediately. 3) A manual `refresh()` while a poll is in flight coalesces — one network request, not two, for the same key. 4) `pages/SkillsSettings.tsx` renders the skill list from the registry with per-skill readiness state, and toggling a skill off writes its name into the `disabled` list of `skills_config.yml` under `data_dir()`; after the toggle, `disabled_skill_names()` includes that skill and the matcher omits it. 5) Both `useDashboardTurnReflection` and `useBeingEvents` route reconnect through the shared policy: fixed 5 s / 3 s constants are gone from those files, backoff doubles from the ~3 s floor toward a ~60 s cap with reset on open. 6) On a WebSocket/EventSource close with code 1008, both hooks stop retrying and surface a reauthenticate state — verified by a test that drives a 1008 close and asserts no further connect attempt is scheduled. 7) No model name appears anywhere in the new page's strings; no emoji; all colours resolve to shared-tokens (scripts/check_contrast.py clean).
