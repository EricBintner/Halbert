## 1. Packet

**DIAG-01** — halbert doctor findings registry + --json + /api/diagnostics.

## 2. User problem

Halbert speaks as the computer itself, grounded in measured data — yet today it cannot answer "are you healthy?" from measurement. Three live defects converge here. (1) `halbert_core/halbert_core/utils/health.py` is a 267-line health-check framework (`HealthCheck`/`SystemHealth` dataclasses, per-check ok/degraded/unhealthy states, checks for Ollama, disk, memory) that nothing imports; the only health surface is a flat `{"status":"healthy"}` JSON from `dashboard/routes/agent.py:2095` (`@router.get("/health")`) that reports agent-session counts, not machine health. (2) `scheduler/autonomous_tasks.py:221` `SystemHealthCheckTask.execute()` gathers real measured state via psutil (cpu_percent, memory, disk, load) and then throws it away — it calls `self._make_decision(...)` which routes to `model_manager.generate(...)` (line 156) and asks an LLM to decide whether the machine is healthy. That directly violates the standing directive "never a model where a template suffices" and the Tier-2 rule's general form: deterministic thresholds, never a judgement call. (3) There is no unified diagnostic sink: R-03's scheduler durability markers (ticker_heartbeat/ticker_last_success/ticker_last_error on disk), R-13's slot-locality results, R-05's redaction coverage gaps, and DIAG-02's store probes all have results worth surfacing, but each would today need its own endpoint, its own shape, its own surface. The founder cannot run one command (`halbert doctor`) or hit one endpoint (`GET /api/diagnostics`) and see an ordered, provenance-annotated list of what is wrong and what to do about it. OpenClaw's reference (src/flows/health-checks.ts:35 + health-check-registry.ts: ordered check registry, checkId ≈ domain+code, fixHint ≈ remediation) shows the shape; Halbert's addition is `why_trust` — provenance refs in the style of `findings/store.py`'s Four Whys — which has no OSS equivalent and is what makes each finding defensible when the founder asks "why do you say that?"

## 3. What to build

Build the doctor as one registry, one Finding shape, two renderers, zero models.

**New module `halbert_core/halbert_core/obs/doctor.py`** (obs/, not a new diagnostics/ package — obs/ is the observability hub: audit, logging, tracing already live there):
- `DiagnosticFinding` dataclass: `domain` (str, e.g. "disk", "scheduler", "store", "slots"), `code` (str, stable machine id within the domain; domain+code is the registry key, mirroring OpenClaw's checkId), `severity` (literal "ok" | "info" | "warning" | "critical" — superset of findings/store.py's info|warning|critical so passing checks can render), `message` (str, first-person measured statement: "My boot disk is 91% full (14.2 GB free)", never "the system may be experiencing"), `why_trust` (list[str] provenance refs: file paths, psutil field names, ticker marker paths — same role as Finding.why_trust in findings/store.py:52), `remediation` (str, concrete staged action or setting path; never an executed command — commands are staged, never executed).
- `doctor_check(domain, code)` decorator registering `(domain, code, fn)` into an ordered module-level `_REGISTRY` list; each check fn returns a `DiagnosticFinding` (always yields one, severity="ok" when the probe passes — the registry is the universal sink, a silent pass is a finding too).
- `run_doctor() -> list[DiagnosticFinding]`: runs the registry in order, catches per-check exceptions and converts them into a `DiagnosticFinding(domain="doctor", code="check_crashed", severity="warning", ...)` naming the crashed check — a broken probe must degrade to a finding, never kill the run.
- `to_json(findings) -> dict`: `{"generated_at", "host" (the onboarding ai_name, never raw hostname), "overall" (worst severity), "findings": [...]}`.

**Initial checks shipped in this unit** (each a small fn in obs/doctor.py or an adjacent module it imports): disk threshold check (psutil.disk_usage on the data dir's filesystem, warn 85% / critical 95%); scheduler liveness check (reads R-03's on-disk ticker_heartbeat/ticker_last_success/ticker_last_error markers — read-only consumer of R-03 output, not a duplicate); configured-vs-observed slot drift check (reads models.yml slot config and compares `:cloud` tags against `is_local_model()` in model/llm_config.py:181 — the one choke point; reports drift as slot labels and resolution status only, never model names, per the founder directive). These three ground the registry; every later workstream residual appends a new registered check.

**CLI: `halbert doctor [--json]`** — add an argparse subcommand in `dashboard/__main__.py` (the `halbert` console script target, pyproject.toml:134). Current main() (line 109) is a flat ArgumentParser with --port/--host/--reload etc.; introduce `add_subparsers()` with `doctor` as the first subcommand, defaulting to the existing server path when no subcommand is given (no back-compat shims needed beyond that — no users yet). `halbert doctor` prints human-readable lines ordered by registry order; `halbert doctor --json` prints to_json() to stdout. Exit code: 0 if no finding worse than "info", 1 if any "warning", 2 if any "critical" (measured, scriptable).

**Route: `GET /api/diagnostics`** — new `halbert_core/halbert_core/dashboard/routes/diagnostics.py` with `router = APIRouter()`, one GET handler calling run_doctor() and returning to_json(). Register in `dashboard/app.py` alongside the other mount_api calls (~line 1093): `mount_api(diagnostics.router, prefix="/api", tags=["diagnostics"])`. mount_api attaches require_owner by default (app.py:1075-1087) — diagnostics is owner-only, which is correct: findings can reference paths and config state. Do NOT add the route to the auth-exempt list in dashboard/auth.py:69.

**Wire the dead framework:** `utils/health.py`'s `HealthCheck`/`SystemHealth` become the per-check primitives behind the existing agent `/health` where relevant, or — cleaner — doctor checks call into its check functions (check_ollama etc.) and translate HealthCheck.status into DiagnosticFinding severity. Either way: delete nothing user-facing, but the framework stops being dead code.

**Delete the LLM judgement:** in `scheduler/autonomous_tasks.py`, `SystemHealthCheckTask.execute()` (line 228) stops calling `_make_decision`/`model_manager.generate`. Replace with: run the doctor registry (import obs.doctor, call run_doctor()), write the findings to the memory_writer outcome log as structured data, and set requires_approval from a deterministic rule (any critical finding → true). The task's `_gather_system_state()` psutil block is retained and becomes the measured input the doctor's checks read. The `model_manager` constructor param stays (AutonomousTask base) but the health task no longer uses it — no model anywhere in a doctor check.

## 8. UX rationale

Two surfaces, one payload. CLI: `halbert doctor` prints one line per finding in registry order, worst-first summary at top: "3 warnings, 0 critical" then lines like "warning  disk/boot-full     My boot disk is 91% full (14.2 GB free). Free space or move the data directory." — first person, measured numbers, no emoji, no model names, slot labels only. `halbert doctor --json` emits the to_json() dict on stdout; the "host" field carries the onboarding ai_name, never the raw hostname (engaged-surface naming rule applies to CLI output too). Exit code 0/1/2 lets launchd or a shell check react without parsing. API: `GET /api/diagnostics` returns the same JSON, owner-authenticated via mount_api's default require_owner; the dashboard and the future support bundle consume this endpoint, so its schema is the contract — stable keys generated_at/host/overall/findings[{domain,code,severity,message,why_trust,remediation}]. why_trust renders as provenance refs a technically-minded founder can follow (e.g. "psutil.disk_usage('/System/Volumes/Data').percent", "scheduler/ticker state: ticker_last_success=2026-09-11T07:12Z"), which is what lets Halbert say "I measured this" credibly when asked. remediation strings are imperative staging text ("Stage: move ~/.halbert/data to a volume with >20% free"), never commands that ran. Overall status rolls up worst severity so a glance answers "are you okay?" — and the answer is always derived from thresholds, never from a model's opinion.
