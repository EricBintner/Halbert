### What Halbert has here today

Halbert's MCP boundary is, on the parts it chose to own, stronger than either origin: an egress redaction choke point with the universal camera gate (`mcp/response.py`, redaction registry from packet 05-A/C2, echo guard from 05-B2/C1), protocol-version validation, serialized session-expiry recovery (`mcp/client.py:757-800`), per-call fail-closed classification when a server vanishes from config, diff-based refresh that keeps a down server's tools, a hardened HTTP server with an 18-tool surface (`mcp/server.py`, TOOL_HANDLERS at :849, dispatch at :1256-1281), and stdlib-only stdio/HTTP transports (`mcp/client.py`: stdio via `asyncio.create_subprocess_exec` at :266, HTTP via `requests.post` at :580). The client advertises only `{tools, resources}` (`client.py:206`) and answers every server-initiated request with JSON-RPC -32601 (`client.py:392`). Tool risk is classified per call from `mcp_config.yml` (`mcp/config.py:52-70` → `tools/mcp_safety.py`, most-specific-first scope rules at `:197-215`); the write path `dashboard/routes/mcp.py:132-164` refuses a literal `auth.token` and carries only `token_env`. Health is a per-process monitor with exponential reconnect backoff (`mcp/health.py:427-465`) that discovers eagerly at agent init (`dashboard/routes/agent.py:367-371`). The channel layer is the wave-3/4 lift: `agents/channels.py` registers exactly three human ingress channels (dashboard, voice, terminal), `resolve_channel` raises `ChannelRefused` for anything else (`:180-190`), `CHANNEL_CLAIM_STAMP` (`:140-144`) stamps the claim source server-side, and the turn-event tee and relay receipts sit beside it. The dashboard's live streams are one SSE-over-fetch-POST agent stream (`dashboard/frontend/src/hooks/useAgentStream.ts:476,1080-1208`) and three WebSockets (`dashboard/routes/websocket.py:45` broadcast, `:79` terminal, `:160/:191` audio). The interrupt algebra is in-process only (`agents/turn_activity.py:23-60`, a `threading.Lock` plus a monotonic generation counter). Pairing (LD-1) has a Settings › Linked Devices UI and host-side approval since `5ab70760`; the pairing-hardening items from this pass (OC19-…-C1/C2, OC17-…-M2, A12-G9) landed in the permissions-consent-security workstream and are only cross-referenced here.

What is weaker than the origins, and what this section is about, is the CLIENT-side trust boundary — what a third-party MCP server process can do to the host — plus the channel layer's inability to express a machine-caused turn, and the absence of any reconnect-without-loss contract on the dashboard's event streams. Already lifted and not re-proposed: redaction variant registry + echo guard + camera gate (05), channel registry + server-stamped claims + turn-event tee + terminal channel (C1/C5), interrupt algebra (07), relay receipts (04). The OpenClaw review's §9 (`OSS-REVIEW-OPENCLAW-2026-09-07.md:135-143`: one policy pipeline, guest-value ownership transfer, order-stable tool naming, host-armed self-management approvals) and the Hermes review's MCP paragraph (`OSS-REVIEW-HERMES-2026-09-07.md:88`: dual-gate validation at save AND spawn time, IOC hardening) named the posture; neither prior pass produced a packet for the client-side boundary, and the master plan's deep-pass agenda item 7 ("Channel design") is where the talk-door items below belong.
