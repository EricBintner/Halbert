### Open founder decisions

1. "When a skill's `requires` does not hold on this machine, does it vanish from `<available_skills>` entirely, or stay listed with a `setup_needed` note so the model can tell me what to configure?" Recommended default: vanish from the model-facing catalog; the readiness note lives on the operator surface (`halbert skills list --all` and the dashboard skills panel). The catalog is the honest set of things runnable now; configuration advice is an operator conversation, not a router input.
2. "May a single model response carry more than one tool call, all executed in order through the same gate?" Recommended default: yes, sequential, each call individually gated and staged; a confirmation on call N stages N+1.. rather than dropping them; only then does the prompt get the batching clause. Today the second call is silently lost.
3. "Does the safety prompt tell the model to refuse to explain code on this machine that looks malicious, or only to infer intent from context before acting?" Recommended default: intent inference only. The owner owns the files; refusing to explain them costs more than it protects on a single-user host. Execution stays gated by the deterministic lattice regardless.
4. "Is `/review` a queued job under the dispatch-side whitelist that reports one system-authored row into the current thread, with no model name and no glyph in that row?" Recommended default: yes — no cache-parity fork (design §5), findings-stream summary plus the one row; the review is bound by the skill ids in the turn's `skill_events`.
5. "Is `/plan` enforced by a per-turn write-plane deny on the executor, with the Hermes prompt text as explanation only?" Recommended default: yes — deterministic policy; a prompt asking a model not to mutate is the weak form Halbert has already rejected for staged commands.
6. "Do proposals on the approval surface carry the alternatives that were rejected and a definition of done, rendered only when more than one remedy exists?" Recommended default: yes; single-remedy proposals render as today.
7. "Curator defaults: deterministic inactivity sweep on (weekly, idle-triggered, with the four never-punish-unobserved-state rules), LLM consolidation off, pins bypass every auto-transition, archive never delete, and the design's 30-day draft expiry counted from first observation rather than from `created_at`?" Recommended default: exactly that; the LLM half stays a separate opt-in with M5's reconciliation as its acceptance test.
