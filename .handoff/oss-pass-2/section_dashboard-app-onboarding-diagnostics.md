### Open founder decisions

- **FD-1 (DAEMON-01):** "When the app is launched while a backend already holds this data dir, should the shell attach to the incumbent, or refuse and show the holder's pid and port?" Recommended default: attach when the incumbent answers `/health` with a matching data dir and version, refuse otherwise; never spawn a second backend on a second port.
- **FD-2 (TERM-02):** "May the agent read the contents of a user-owned shell pane, and is that a capability with its own consent row (per capability boundary), or part of the terminal channel already granted?" Recommended default: its own capability (`terminal.read_user_pane`) defaulting on for the owner, denied for guests, with the read passing the display seam and echo guard.
- **FD-3 (BIND-01):** "Do we want a structured 'hand back a generated file' convention in chat at all, given the owner already has the filesystem and it opens an exfiltration surface?" Recommended default: no for now; ship only the resolve-before-check strengthening of `SENSITIVE_PATHS`.
- **FD-4 (BIND-01):** "Should each stored credential carry an allowed-hosts list enforced at egress?" Recommended default: yes, deterministic and off-by-default per credential (empty list = provider's own host only), since it complements the Tier-2 posture without a model.
- **FD-5 (SURFACE-01):** "Does a per-task progress card belong in the Workloads rail / Presence Pill, or is it a session-list by another name?" Recommended default: yes as a turn side-car (tombstoned when idle, never a list of conversations).
- **FD-6 (SURFACE-01):** "What does the live status strip show while a guest persona fronts — verbs only, or the owner's full argument previews?" Recommended default: verb-only while fronting, full previews for the owner.
- **FD-7 (TERM-02):** "May the agent propose installing or enabling an MCP server as a staged card (agent proposes, human approves via the existing consent surface)?" Recommended default: hold until the B6 MCP-server audit closes; if approved, it is staged-never-executed with the three outcomes (unanswered / declined / approved) distinct.
- **FD-8 (Theme 11):** "Is a first-party backup of Halbert's own state on the roadmap, given 'no migrations, leave old data unread, never delete'?" Recommended default: not now; the freshness split and archive-verification checklist attach to whichever issue adds it.
- **FD-9 (DIAG-01):** "Does `halbert doctor --fix` execute repairs directly, or does every repair become a Finding proposal through the existing approval queue?" Recommended default: proposals through the approval queue, with a CLI `--yes` that approves in place — one policy pipeline, commands staged never executed.
